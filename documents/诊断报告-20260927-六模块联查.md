## 1. 微信连接（P0，已修复）

### 证据链

- `logs/main.log` 17:16–17:21 三次重复崩溃栈：
  `ILinkProtocolError('ret must be an integer')`
  → `communication/ilink/models.py:60 _integer`
  → `models.py:220 GetUpdatesResponse.from_dict`
  → `communication/ilink/client.py:85 get_updates`
  → `core/ilink_gateway.py:117 _poll`，`Task ... done ... exception=...`
- 真机探测（已存凭据实调 `POST /ilink/bot/getupdates`，HTTP 200）：成功包体只有
  `{"msgs": [], "sync_buf": "...", "get_updates_buf": "..."}`——**成功时根本没有 ret 字段**。
- `core/ilink_gateway.py` `_poll()` 只兜了 RateLimit / SessionExpired / 5xx HTTP / 网络错误，
  未兜 `ILinkProtocolError`，一个空消息轮询就把整个通道任务打死，状态永离 connected。

### 修复（已做）

1. `communication/ilink/models.py:220`：`ret` 改可选，缺失即 0。
2. `core/ilink_gateway.py`：`_poll` 捕获 `ILinkProtocolError`，退避重试（游标仅在解析成功后推进，重试安全）。
3. 78 个 ilink 测试全过。

### 修复前后对比（运行时证据）

- 修复前：首个 poll 即 `ret must be an integer`，任务死亡，前端无法连接。
- 修复后：后端连续多轮 `getupdates 200`（00:25:30 起约每 18s 一次），零协议异常，
  `GET /api/ilink/status` → `phase=connected, configured=true, connected=true`。

### 1b. 遗留：配对码闭环缺失（P1，必须补否则微信仍无法真正对话）

- `core/ilink_state.py:108 create_pairing_code` 已实现，但**全项目无任何调用方**；
  `core/api_server.py` 无 `/api/ilink/pairing-code`；
  前端 `external-connections-panel.js` 无配对码 UI（只有一个 `pairing_required` 状态名）。
- 后果：gateway 连通后，微信用户发的消息在 `channel._handle_message` 因无 binding
  走 `verify_pairing`，库里无配对码记录 → 永远 False → 消息静默丢弃，伊塔不回复。
- 方案：新增 `POST /api/ilink/pairing-code`（经 gateway 当前 bot_id 生成，返回码+有效期+失败次数）；
  status 增加 `pairing: {required, expires_at, attempts}`；面板 connected 未绑定时展示
  「请在微信向机器人发送这 8 位数字」；绑定成功后状态转 `bound`。

## 2. 图像生成

### 2a. 9/26 午夜「图片这次没发出来」=世界闸门关闭（与 #3 同根）

- `logs/main.log` 23:52–23:58 四条：
  `[ChatPhoto] delivered status=disabled reason=world_disabled consumed=False`
  与截图时间（23:57/23:58）完全吻合。
- 链路：`core/pipeline.py:1281 _deliver_chat_photo` →
  `Companion.publish_image_candidate`（`core/companion.py:1633`）→
  world outbox 发布/消费；`world_port` 为 `NullWorldAdapter` 时
  `control/publish` 一律 `world_disabled`（`core/world_port.py:237/243`）。
- 即这次图根本没走到生图 provider，前置闸门就拒了。修好世界模块（#3）即解除。

### 2b. 「再拍一张」行为错误（P1）

- `electron/src/renderer/js/chat.js:428-436`：点击后把 `retry_text` 填入输入框并调 `this.send()`
  ——把用户原指令当**一条新消息**重发（还会再走一遍意图识别/分条），不是重跑生图。
- 同一气泡 `_upsertImageStatusBubble`（chat.js:441-476）直接 `appendChild`，
  **绕过 chat-store 排序**，是 #4 气泡错位的来源之一。
- 正确做法：调 `POST /api/images/generate`（`core/api_server.py:2450`），
  用原 prompt_key/user_raw/size/reference_assets/persona_id 组参，新幂等键（`:retry<n>`），
  不产生用户消息；图片状态气泡改走 store upsert。

### 2c. provider 层历史失败（P2，待核实）

- 9/25 19:38 有 `image provider network call failed` / `image edit provider call failed`；
  `core/llm_caller.py:1494 generate_image` 是 stub，真实链路在 `core/image_service.py:581`
  → ai_services `key="image"`（`core/ai_services.py:173`，env `IMAGE_GEN_MODEL`，默认 gpt-image-2）。
- 9/26 午夜失败未到达该层，**没有证据表明前期 API KEY 修复引入回归**；
- 待世界闸门解除后做一次真实生图探活，若 401/key 缺失再查 settings/env 解析（llm_caller.py:460-497）。

## 3. 世界模块第二波启动（P0）

### 3.1 sidecar 数据库无限膨胀（直接卡死启动）

- `data/world_sidecar/world.db` = **1,065 MB（1.1GB）**：
  `world_outbox` 845,303 行、`world_state_snapshot` 845,197 行。
- `world_service` 全目录 grep 无任何 `DELETE/prune/retention/VACUUM`；
  `world_service/main.py:40` 默认 `tick_interval_seconds=1.0`，
  `storage/sqlite_store.py:47,65` 每 tick 各插一行 → 一天 8.64 万行、约 100MB/天。
- `plugin-supervisor.js:408-451` start 要在 `startupTimeoutMs` 内完成
  ready 行 + `/hello` 握手 + `/state` 读取；GB 级库恢复/查询直接超时
  → `startup_failed`/`recordCrash`，表现为「第二波起不来」。
- 修复：
  1. 立即处置：停 sidecar 后对两表做保留窗口清理（如 outbox 仅留 ACK 后 N 条/7 天，
     snapshot 每 N tick 留 1 条 + 保留最近 M 条）并 `VACUUM`；
  2. 长期：sqlite_store 增加 tick 内增量修剪（保留上限+年龄），加用户态
     `POST /api/world/maintenance` 或启动前自动修剪；
  3. tick 快照降频（状态未变不写 / 改 5–10s 一档）。

### 3.2 双世界架构与状态不一致

- 存在两个世界：后端进程内 `InProcessWorldAdapter` 与 Electron 监督的 sidecar
  （`world_service.main`）。`build_world_port`（`core/world_port.py:659-707`）
  先试 sidecar（env endpoint/token 缺失即记 `failed to initialize remote world adapter`，
  日志 17:13/17:14 多条），再回退 inprocess。
- `data/runtime_config.json` rev14：`world_sidecar_v1=false`、
  `world_process_supervision_v1=false`、`world_runtime_loop_v1=false`、
  `world_desired=running`——即运行时层关了 sidecar，但静态 `config/settings.yaml`
  三 flag 均为 true；仪表盘「功能 enabled=true」来自静态值，
  Electron 实际不 spawn（`main.js:2265-2305` 三条件与运算）。
- 当前实测后端：`/api/world/dashboard/snapshot` = `running/simulated`（进程内世界正常 tick）。
  午夜 disabled 疑似当时后端 world_port 曾被
  `POST /api/world/runtime/bind` connection=null 覆盖为 NullWorldAdapter
  （该路径已有 InProcess 保护，`api_server.py:896-905`，需确认当晚运行版本是否含此修复）。
- 修复方向：统一「单一世界模式」事实源——运行时 flag 决定时，静态面板不得显示 enabled；
  inprocess 模式下隐藏/禁用 sidecar 生命周期控件，避免两套状态互相覆盖。

## 4. 消息排序、时间戳、气泡错位（P1）

- 存在双渲染路径：`chat-store.js:77-160` 有 `insertSorted`/`sortKey{ t,b }`/upsert 重排，
  正常消息（用户、助手分片、typing）走 store；但
  `chat.js:441` 图片状态气泡、审批卡片等直接 `appendChild` 到消息容器，完全不受排序约束
  → 异步任务中这些气泡先于/后于用户消息出现，截图所示倒置由此产生。
- 时间戳同源：`core/chat_request_repository.py:225-233 submit_batch` 对一批用同一个
  `_timestamp()`；截图同一轮三条助手消息同为 `00:08:04`。前端同秒依赖
  insertCounter/domId tiebreak，但旁路 append 的元素没有序号。
- 用户消息异步回填：乐观气泡、typing 占位与真实消息 upsert 在长任务期间可能晚于助手节点，
  重排只覆盖 store 内节点。
- 修复：所有气泡（含 image-status/approval/tool 状态）一律走 store upsert；
  后端每个分段独立时间戳（段内可保留批次 id），store tiebreak 用
  `(ts, batch_seq, insertCounter)`；回填用户消息时强制重排整列。

## 5. 「生成中」状态体验（P2）

- 现状：`chat.js:1776` request 状态文案 `running: "生成中"`，
  样式 `main.css:1645` 的 badge；与「排队中」一样挂在气泡旁，语义不清（实际是 AI 处理中）。
- 方案：running 时在助手头像前显示三点跳动 typing 气泡（复用现有 typing 样式），
  不出文字 badge；排队中保留可取消 badge。注意宿主只能是助手节点（chat.js:1791 注释已有此约束）。

## 6. 连续多句被拆成独立任务（P2）

- `core/message_batcher.py:133-173` 现语义：首条**零等待立即 dispatch**（Gate4 为修 D5 刻意改的），
  运行中到达的才进 pending。空闲时连打两句 → 第一句立刻开跑，第二句成为下一批 → 上下文断裂。
- 方案（需权衡首条延迟）：首条派发前加可配置短静默聚合窗（建议 1.2–2.0s，
  沿用 `window_seconds`，timer 内续到消息则重置，上限 max_batch_size）；
  本地桌面/QQ 同通道一致生效；设置页可开关与调窗长。

## 耦合风险评估

- 世界闸门同时挂着生图（publish_image_candidate）与仪表盘，修 #3 会直接改变 #2a 行为，需回归生图。
- chat-store 收口所有气泡会触碰审批卡片/工具调用/图片三类旁路节点，需跑
  `electron/tests/chat-request-queue.test.js` 全量。
- 微信 gateway 容错改动影响所有 iLink 长轮询，78 测试已过，真机需观察 24h 无任务死亡。
- runtime_config 双 flag 事实源横跨 Electron main 与后端，改动需两端同步重启验证。

## 建议修复批次

1. **批次 A（P0）**：微信协议崩溃（已完成）→ 世界库修剪+retention+启动前自检 → 生图闸门验证。
2. **批次 B（P1）**：配对码闭环、消息渲染统一收口+分段时间戳、再拍一张重跑生图。
3. **批次 C（P2）**：生成中 typing 化、batcher 静默聚合窗、生图 provider key 探活。
