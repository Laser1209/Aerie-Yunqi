# Bug 猎手（dogfood）

当你要像真实用户一样去"用"一个 Web 应用、主动找它的毛病时走这份流程。产出是一份**可复现、带证据、按严重程度排序**的缺陷清单，而不是一句"整体感觉还行"。

## 铁律

1. **每条缺陷必须有可复现步骤**：从哪一页、点了什么、输入什么、看到什么、期望什么，一步步写清，别人照着能重现。
2. **证据优先**：能截图就截图，能贴控制台报错就贴，能给出失败请求就给出；没有证据的结论只算"疑似"。
3. **先广度后深度**：先把主干流程走一遍找出明显的坏点，再挑关键路径深挖边界，别一上来就抠细节。
4. **专挑边界与异常**：空输入、超长输入、特殊字符、重复提交、断网、快速连点、后退刷新——缺陷基本都藏在这里。
5. **区分缺陷与设计选择**：与需求不符、报错、崩溃是缺陷；只是你觉得不好看，算体验建议，分开列。
6. **给严重程度定级**：崩溃、数据丢失、阻塞主流程为高；体验受损为中；文案或样式瑕疵为低。

## 步骤

1. **列测试范围**：要测的功能清单与主干用户路径（注册、登录、下单、导出等）。
2. **走一遍主干**：逐条路径操作，记录任何异常、报错、卡顿、结果不符。
3. **补边界用例**：对每个输入做空值、极值、特殊字符、重复提交、快速连点。
4. **看控制台与网络**：打开开发者工具，收集 JS 报错、失败的请求（4xx/5xx）、慢请求。
5. **记录缺陷**：每条写清标题、复现步骤、期望与实际、证据、严重级别。
6. **排序与去重**：合并同类项，按严重级别从高到低排列，标注影响面。
7. **给出结论**：说明是否可发布、阻塞项有哪些、哪些属于建议。

## 输出形态

```
## 结论
- 可发布 / 有阻塞项：<列出>

## 缺陷清单
### [高] 提交空表单后白屏
- 复现：打开 /signup → 直接点"注册"
- 期望：提示"请填写邮箱"  实际：页面白屏，控制台报 TypeError
- 证据：screenshot-01.png、console 报错堆栈

### [中] …

## 体验建议（非缺陷）
- …
```

## 反面例子（不要这样）

- "整体体验不错，没有明显问题"——没有任何一条可复现的缺陷。
- 只点了一遍首页就下结论，没走主干流程也没碰边界。
- 把个人审美（按钮不够圆）当缺陷，混进阻塞项里。
- 报了 bug 却没有复现步骤，开发无法定位。
