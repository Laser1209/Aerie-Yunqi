# Web 应用测试（webapp-testing）

当你要用 Playwright 对本地运行的 Web 应用做真实浏览器验证——点击、填表、断言、截图、看控制台——时走这份流程。产出是**可复现的操作脚本 + 断言结果 + 日志证据**，说明功能是否按预期工作。

## 铁律

1. **先起服务再测**：确认本地服务已在监听并记录端口，测试脚本连不上就无从谈起；不要假设服务自己会起来。
2. **用稳定的定位器**：优先 `get_by_role` / `get_by_label` / `data-testid`，避免依赖会变的结构或文案，否则改个样式测试就碎。
3. **等待用自动等待，不用 sleep**：Playwright 默认对可见性与可点击性自动等待，只在万不得已时才显式等待条件，绝不写 `sleep(3)`。
4. **每条断言对应一个行为**：断言"点提交后出现成功提示"，而不是断言内部状态；一个用例只验证一到两件事。
5. **必须收集控制台与网络**：挂上 console 与 pageerror 监听、记录 4xx/5xx 请求，前端 bug 大多藏在这里。
6. **失败留下证据**：出错时截图、打印控制台、保存 trace，方便复现，别只回一句"断言失败"。

## 步骤

1. **确认服务**：拿到本地地址与端口，先手动请求一次确认可访问。
2. **写最小脚本**：启动浏览器、打开页面、等待关键元素出现，先证明"能连上、能渲染"。
3. **走关键流程**：按用户路径依次操作（填写、点击、跳转），每步都用稳定定位器。
4. **加断言**：对每个关键节点断言可见性、文本或状态变化。
5. **接日志**：注册 console / pageerror / requestfailed 监听，把异常收集到列表。
6. **跑并收集**：执行脚本，失败时截图、输出控制台与失败请求。
7. **汇总结论**：列出通过的流程与失败的流程，附证据定位。

## 输出形态

```
## 环境
- 地址：http://localhost:5173  服务：vite dev

## 用例结果
- [通过] 打开首页并渲染标题
- [失败] 提交登录表单 → 期望跳转 /home，实际停留原地
  - 控制台：POST /api/login 500
  - 证据：login-fail.png

## 日志摘要
- console errors: 2  warnings: 1  failed requests: 1
```

## 反面例子（不要这样）

- 服务没起就写脚本，报 connection refused 还反复重试。
- 满屏 `sleep(2)` 掩盖竞态，跑得又慢又不稳。
- 用 `page.click("div:nth-child(3) > button")` 这种一改就碎的定位器。
- 断言失败只说"没过"，不给截图也不给控制台。
