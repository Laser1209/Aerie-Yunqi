# Spec 拆成任务（notion-spec-to-impl）

把 Notion 上的一份规格（PRD / 需求文档）拆成**可执行、可跟踪、互相链接**的
实施计划与任务条目。

判断标准只有一条：**执行的人拿到任务条目，能不能不问人就开工**。

## 前置

凭据与通道都在设置页：先在「平台凭证 → Notion」填个人访问令牌，再到
**「MCP 服务器」里开启 Notion**（改完需重启后端生效）。

**如果当前没有 `mcp__notion__` 开头的工具**，说明通道没开。这时**直接告诉用户去开启**，
不要凭空编出一份"我拆好了"的任务清单。

## 铁律

1. **先读原文再拆**：搜到规格页后完整读一遍，提取需求、验收标准、约束、优先级。
2. **先记录疑问，再动手**：把规格里的歧义与假设写成一个"待确认"清单，
   放在计划页最前面。含糊的规格直接拆，只会拆出一堆返工。
3. **任务粒度 1~2 天**。超过就再拆；小于半天就合并，否则看板会变成噪音。
4. **每个任务自带上下文**：目标、验收标准、依赖、所需资料。缺这些就不算任务。
5. **三重链接**：计划 → 规格，任务 → 计划 + 规格。断链的任务过两周没人知道为什么存在。
6. **只改该改的**：往规格里补"实施"小节时，先取回当前内容再做精确替换；
   只改属性时不要顺手改正文。

## 步骤

1. 搜索定位规格页，必要时问用户是哪一个；完整读一遍。
2. 抽取需求/验收标准/约束/优先级，输出"待确认"清单。
3. 选计划深度：小改动用快版，多阶段特性或迁移用标准版。
4. 建计划页：概述 → 链接规格 → 需求摘要 → 阶段划分 → 依赖与风险 → 成功标准。
5. 找任务资料库并确认字段（状态、优先级、关联、截止/工作量/负责人）。
6. 建任务条目：动词开头的标题 + 上下文 + 目标 + 验收标准 + 依赖 + 资料链接。
7. 连好链接；需要的话在规格页补一个"实施"小节指向计划与任务。
8. 跟踪：定期更新状态与检查清单；阶段收口时写小结；阻塞与决策记下来。

## 自检

- 执行人不问人就能开工
- 每个任务都能追到规格里的具体条目
- 任务粒度在 1~2 天量级
- 待确认清单已交给用户，且没有把假设当结论
- 计划页、任务、规格三者互相可达

## 反面例子

- 把规格的章节标题直接当任务，没有可执行内容
- 任务没有验收标准，"做完了"全凭感觉
- 规格里明明有歧义，却按自己的理解拆了
- 任务建完不关联规格，过两周没人知道它从哪来
