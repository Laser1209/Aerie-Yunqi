# 11-统一命名与模块收敛改造计划

本文基于 [[10_模块依赖关系图]] 的真实 import 证据，给出「统一命名 + 模块收敛」的改造计划，并附**现状达标评估**（回答：现在代码达到这个标准了吗？）。

> [!important] 改造总原则（来自项目规则）
> 1. **不保留向后兼容**：过时的直接删，不加兼容层、不写 migration、不留 fallback。
> 2. **选满足当前需求的最简单实现**：不预防性抽象、不多余配置层。
> 3. **先跑通最小端到端，再往上加**：绝不为未完成的复杂度拆掉能跑的东西。
> 4. 优先成熟库，不自己重写；先翻已有依赖能做什么，再考虑加包。

### 2.3 认知/决策边界（P2 — 实锤：决策引擎死代码 + 失效）

> [!danger] 一句话结论
> **`core/decision.py` 的 L1-L4 多层决策引擎从未被装配、且一旦调用必然崩溃（KeyError）——整段是死代码 + 坏代码。** `pipeline`（编排）与 `agent`（第二编排）存在重复，`cognition`（追踪）职责干净。

#### 边界现状（实锤核实，四模块职责与调用链）

| 模块 | 职责 | 关键证据 | 健康状况 |
| --- | --- | --- | --- |
| `pipeline.py` `Pipeline` | 9 阶段流程编排 + 持久化 + emit + send_queue | `handle()`（[pipeline.py L121](file:///e:/Agent_reply/core/pipeline.py#L121)）串起 route→emotion→context→brain→tools→postprocess→output | ✅ 编排清晰，但塞了过多业务（见 P2-C） |
| `cognition.py` `CognitionEngine` | **纯认知追踪**：begin/record/commit + patch | [cognition.py](file:///e:/Agent_reply/core/cognition.py) 只有记录/持久化/SSE，**无决策逻辑** | ✅ 职责单一（有 commit-too-early 味道，见 P2-E） |
| `decision.py` `MultiLayerDecision` | L1-L4 加权决策 + softmax | [decision.py](file:///e:/Agent_reply/core/decision.py) | ❌ **死代码 + 必崩**（见 P2-A/B） |
| `agent.py` `Agent` | 装配入口 + 六步循环（Perceive→Reason→Decide→Act→Reflect→Express） | [agent.py](file:///e:/Agent_reply/core/agent.py) | ⚠️ 与 pipeline 重复编排（见 P2-C） |

**调用链**：`pipeline/agent`（编排）→ `cognition`（记录）＋`decision`（决策，实际未接）→ `brain`(LLM) / `emotion` / `tools`。

#### P2-A 【严重】决策引擎必崩：`KeyError: 'L1'`

> 实测：`python -c "from core.decision import MultiLayerDecision; MultiLayerDecision().decide_for_message(1,'FULL','local')"` → **`KeyError: 'L1'`**（[decision.py L121](file:///e:/Agent_reply/core/decision.py#L121)）。

根因是 [decision.py L121](file:///e:/Agent_reply/core/decision.py#L121) 的权重查找：
```python
weight = self.WEIGHTS[f"L{layer_name[1]}_" if False else layer_name]
```
`if False` 是**死代码分支**，恒取 `layer_name`（`"L1"`…），但 `WEIGHTS` 键是 `"L1_core"/"L2_personality"/"L3_mood"/"L4_context"`，不存在 `"L1"`。且死分支 `f"L{layer_name[1]}_"` 产生 `"L1_"` 同样不匹配——整行是坏代码。

#### P2-B 【严重】决策引擎从未被装配（死代码）

- `companion.py` L256 构造 `Pipeline` 时**未传 `decision_engine`**（见 [companion.py L256-273](file:///e:/Agent_reply/core/companion.py#L256)）→ 生产 `pipeline.decision_engine = None`。
- 全库 grep `MultiLayerDecision(` **无任何实例化**（生产与测试均无）。
- `agent.py` 通过 `getattr(companion.pipeline,'decision_engine',None)` 取到 `None`。
- 结果：L1-L4 决策 = **从未运行过的死代码**；即便装配也会因 P2-A 崩溃。UI「决策赛马」（T33）**无真实数据源**。

#### P2-C 【中】双编排器重复（pipeline vs agent）

- `pipeline.handle()` 与 `agent.run()` **各自实现完整编排**（感知→决策→工具→持久化→emit→send_queue），代码大量重复。
- `agent.use_agent_path=False`（默认）时降级到 pipeline，形成「双轨」。
- **决策触发点不一致**：pipeline 在 route 阶段只传 `user_id/route_mode/source` 调 `decide_for_message`（缺 emotion/tools/eruption）；agent 在 `perceive()` 传了完整 emotion_label/tools_offered/active_eruption。

#### P2-D 【中】决策结果未实际影响流程

- 即便在 pipeline 装配了 decision_engine，`decide_for_message` 返回值**只 `record_decision` 到 cognition**，不 gate 任何流程分支（[pipeline.py L221-230](file:///e:/Agent_reply/core/pipeline.py#L221)）。`silence`/`tool_call`/`reply` 决策对实际回复零影响。
- agent 的 `decide()` 将 `chosen` 写入 `Decision.intent`，但也只是记录，不阻断回复。

#### P2-E 【低】cognition 的 commit-too-early 味道

- `CognitionEngine` 有 **3 个 patch 方法**：`patch_stage_output` / `patch_decision` / `append_pacing_decisions`（[cognition.py](file:///e:/Agent_reply/core/cognition.py)）。
- 原因：pacing/decision 数据在 `commit()` **之后**才产生（依赖 split 后 segment 与 SendQueue 异步结果）。这是「过早 commit + 事后 patch」的反模式信号。

#### 建议的目标边界

- `pipeline` = **唯一**流程编排器（9 阶段）。
- `cognition` = 纯追踪（begin/record/commit），移除 patch，改为 commit 前备齐数据。
- `decision` = L1-L4 决策模型，由 pipeline 在合适时机调用，**结果真正 gate 流程**（如沉默/工具）。
- `agent` = 收敛为 pipeline 之上的**薄装配**，不重复编排。
