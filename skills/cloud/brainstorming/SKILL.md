# 需求澄清（brainstorming）

在动手做之前，先把"要解决的问题"钉清楚。**不写代码、不给实现方案**，
这一阶段只做澄清与发散。

## 铁律

1. **一次只问一个问题**。把问题堆成清单会让对方只能挑着答，你会拿到一堆残缺答案。
2. **先查再问**。能从现有代码、配置、日志里读到的，不要拿去问人——那是浪费对方的时间。
   问之前先说明你已经看过什么。
3. **听不懂就问，不要猜**。宁可多问一句，也不要基于猜测做出一堆返工的东西。
4. **不做未要求的扩展**。对方说 A，你不要顺手把 B、C 也规划进去。

## 步骤

1. **复述**：用你自己的话把需求说一遍，包括你认为的**成功标准**。
   让对方确认或纠正——这是最便宜的一次对齐。
2. **找歧义**：列出这句话里 2~4 个可以有不同理解的地方，逐个确认。
   典型歧义：范围（做多少）、时机（现在还是以后）、受众（给谁用）、
   底线（什么绝对不能牺牲）。
3. **发散**：给出 2~3 个**互不相同**的可行方向，每个都写清代价与适用前提。
   不要给三个"换汤不换药"的选项凑数。
4. **收敛**：请对方选一个方向，或者告诉你他真正在意的约束是什么。
5. **写出结论**：把最终确认的范围、成功标准、明确的**不做项**列成一小段。

## 输出形态

```
## 我理解的需求
（一句话复述 + 成功标准）

## 需要确认的分歧
1. …
2. …

## 可选方向
- 方向 A：…（代价 / 适合什么时候）
- 方向 B：…

## 确认后我会做 / 不会做
- 会做：…
- 不会做：…（主动写出来，避免后面"我以为你要做"）
```

## 反面例子（不要这样）

- 一口气抛出 8 个问题，然后自己替对方回答。
- 对方还没确认范围就开始给实现细节和代码。
- 把"我觉得应该加个 X"写成需求——那是你的偏好，不是对方的要求。
