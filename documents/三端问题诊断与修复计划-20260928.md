## 二、根因分析

### 2.1 【P0 · 核心根因】`ControlResult` 不可序列化 → 毒化上下文 → 幻觉

**这是本次所有"上下文丢失 + 幻觉"现象的总根因。**

#### 断链位置（代码级）

| 环节 | 代码 | 问题 |
|------|------|------|
| ① 工具注册 | `tools/compute_tools.py`：`registry.register("shell_execute", controller.shell_execute, …)` | 把**返回 `ControlResult` 裸对象**的方法直接当工具注册 |
| ② 工具返回 | `core/computer_control.py`：`def shell_execute(...) -> ControlResult:` | 返回 `@dataclass ControlResult`，**不是 dict** |
| ③ 注册表透传 | `core/tool_registry.py::execute` → `return result` | **原样返回，不做任何序列化归一化** |
| ④ 组装模型消息 | `core/llm_caller.py` → `"content": json.dumps(result, ensure_ascii=False)` | **在这里炸** → `TypeError: Object of type ControlResult is not JSON serializable` |
| ⑤ 异常处理 | 同文件 `except Exception as e:` → `Provider %s failed` | 异常被归因为"**这个供应商坏了**"，换下一个 |

#### 为什么后果这么严重

```python
working_msgs.append(assistant_msg)        # ← 先把 assistant(带 tool_calls) 塞进历史
for tc in new_calls:
    result = await tool_registry.execute(...)
    tool_msg = {"role": "tool", "tool_call_id": tc_id,
                "content": json.dumps(result)}   # ← 这里抛异常
    working_msgs.append(tool_msg)                # ← 永远执行不到
```

于是 `working_msgs` 里留下一条**孤儿 assistant 消息**：声明了 `tool_calls`，却没有配对的 `tool` 回执。

而 `working_msgs` 是**跨供应商复用**的（构造一次，逐个 provider 试）。所以：

> **一个工具吐出一个 `ControlResult`，会让本轮所有剩余供应商全部看到畸形历史。**

日志逐字印证：
```
Provider doubao   failed: Object of type ControlResult is not JSON serializable   ← 源头
Provider deepseek failed: HTTP 400 "An assistant message with 'tool_..."          ← 结构性违规
Provider grok     failed: HTTP 503
Provider openai   failed: HTTP 403
```

deepseek 那条 400 的原文是 OpenAI 兼容接口的标准报错：*"An assistant message with 'tool_calls' must be followed by tool messages responding to each tool_call_id"* —— 这是**孤儿 tool_call 的铁证**。

#### 这一条解释了你观察到的全部现象

| 你的原话 | 机制 |
|---------|------|
| "他一开始想从默认的文件夹里面去找" | 提示词的 L5 方法论写的是 `directory_list/file_search → 确认文件位置`（`core/context_builder.py`），且 office 工具速查清单里**没有 `send_file_to_user`** |
| "我给他路径了" | 13:15:33 同一句里就带了 `D:\Harness创客工坊` |
| "他好像没有继续调取上面的上下文" | **上下文真的被毒化了** —— 4 个供应商拒收后，最终接手的 dashscope 拿到的是一份畸形/膨胀的历史（prompt 从 ~24K 暴涨到 **177,696** tokens） |
| "给自己一个虚假的已转过去的操作" | 工具返回 `{"success": True, "queued": True}`（只代表入队），投递异常被 `except Exception: logger.exception` 吞掉、**不回写模型** → 模型无从得知失败，只能照工具回执说"已发送" |
| "产生了一个相应的幻觉" | 上面两条叠加 |

#### 触发路径（这是本次最关键的因果，请重点看）

```
你要文件
  → send_file_to_user 失败（文件不在授权目录）        〔§2.4 权限设计〕
  → Agent 想"换个方式"：file_copy 到 F:\文件\Aerie     〔被手审策略拒绝〕
  → Agent 再换：directory_create 到 _待发送            〔被手审策略拒绝〕
  → Agent 改用 shell_execute 直接复制                  〔绕路〕
  → shell_execute 返回 ControlResult → 序列化炸        〔§2.1 P0〕
  → 上下文毒化 → 4 个供应商拒收 → 换到 dashscope
  → 模型在残缺上下文里编出"已经发过去啦"
```

**结论：权限设计（正当）→ 逼出绕路（可预期）→ 绕路踩中序列化 Bug（不可接受）→ 幻觉。**

#### 波及范围（不止 `shell_execute`）

日志里 `system_control` 分类共 **12 个工具**，全部由 `controller.*` 直接注册，全部返回 `ControlResult`：

```
file_write, focus_window, hotkey, key_press, list_windows, mouse_click,
mouse_move, mouse_scroll, screenshot, shell_execute, type_text, uia_action
```

> **也就是说：Agent 只要用一次截屏 / 鼠标 / 键盘 / shell，本轮的对话上下文就会被毒化一次。**
> 这是本项目"系统操控类任务容易答非所问"的机制级解释。

**旁证**：被删除的 `core/screen_tools.py` 里有一整套 `tool_screen_*() -> dict` 的**包装函数**（`tool_screen_screenshot` / `tool_screen_shell` / …），说明历史上是有"转 dict"这一层的；现在这条路被改成了直接注册 controller 方法。**这个 Bug 很可能是近期重构引入或放大的**（需与并发开发者核对，见 §0.3）。

#### 2.2.1 三处叠加的技术债（本机代码可证实）

| # | 原因 | 位置 |
|---|------|------|
| 1 | **整块上传**：`ciphertext = encrypted_path.read_bytes()` —— 278 MB 全部读进内存再一次性 POST | `communication/ilink/media.py` |
| 2 | **超时太短**：`httpx.Timeout(connect=10, read=45, write=20, pool=10)` —— 大文件 POST 后等不到响应就判超时 | `communication/ilink/client.py::ILinkClient.DEFAULT_TIMEOUT` |
| 3 | **磁盘双写**：先把 278 MB 加密写一份完整临时密文，再 `read_bytes()` 读进内存 | `communication/ilink/media.py` |

**资源账**：源文件 278 MB + 临时密文 ~278 MB（磁盘）+ 内存 278 MB ≈ **834 MB 峰值**。桌面应用不可接受。

**好消息**：加密本身**已经是流式的**（`media_crypto.py::encrypt_media` 按 64 KB 分块 + AES-ECB，天然支持流式）。**唯一非流式的就是最后这一行 `read_bytes()`。**

#### 2.2.2 平台侧上限：出站**根本没有公开数字**（用户调研，2026-09-28）

这是本次决策的关键依据，我把结论原文登记如下（来源：用户自行调研，我未独立复核）：

| 维度 | 数值 | 性质 |
|------|------|------|
| **入站**（用户 → Bot）单条媒体 | **100 MiB** | **官方硬常量**：`@tencent-weixin/openclaw-weixin@2.4.9` 的 `src/media/media-download.ts` 中 `WEIXIN_MEDIA_MAX_BYTES = 100 * 1024 * 1024`；第三方协议文档亦有"官方入站媒体上限 100 MiB"互证 |
| **出站**（Bot → 用户） | **无公开数字** | 官方 SDK 的 `cdn/upload.ts` / `cdn-upload.ts` **完全没有体积校验**，只有 3 次重试 → 上限发生在服务端/CDN，未文档化、**不返回友好错误** |
| 文本 item | 16 KiB（UTF-8 字节数） | 服务端拒收，`ret: -2` |
| 单个 `context_token` | 最多 10 条回复 | 超限**静默失败** |

**容易被误当"平台上限"的假数字**：

| 流传值 | 真实出处 |
|--------|---------|
| 25 MiB | Koishi 适配器默认值；官方包里 25 MiB 只用于**引用缓存单文件**（配额，非平台限制） |
| 8 MiB | openhermit 出站跳过阈值，理由是"CDN 上传链路慢"，**是它自己的取舍** |
| 20/50/100 MB | `wechat-kilocli-bridge` 的 `WECHAT_MAX_*_MB` 环境变量默认值 |
| "图片超 30 KB 就失败" | 某掘金实测，与其自身网络/代理强相关，与 100 MiB 冲突，**不可采信** |

**这份调研对本次设计的三点直接意义：**
1. **不能靠"事先知道上限"来做闸门** —— 出站上限未知且无错误码，所以**唯一可靠的定阈值方式是本机实测**（见附录 C 探测脚本）；
2. **出站失败必然是"静默/超时"形态** —— 这正好解释了 §2.2 的现象：我们的 `ReadTimeout` 很可能**不是"文件太大被拒"，而是 CDN 侧处理不过来或干脆没接受**。所以**必须靠超时 + 体积双阈值**来判定，不能指望一个明确的错误码；
3. **入站 100 MiB 是官方硬数字，可以放心依赖** —— 这反过来提示：**出站若远超 100 MiB，风险很高**。278 MB 已经是入站上限的 2.8 倍。

#### 2.2.3 流式方案可行性：本机实测结论（**已确认可行**）

我在本机对 **httpx 0.28.1**（项目实际版本）做了三组对照实验，专门验证"能否既流式、又带上 CDN 要求的 `Content-Length`"：

| 传法 | `Content-Length` | `Transfer-Encoding` | 结果 |
|------|-----------------|--------------------|------|
| ① 异步生成器 | ❌ 无 | `chunked` | **会被 CDN 回 500**（上一轮真机已证实） |
| ② 直接传文件对象 | — | — | ❌ **抛 `RuntimeError`**：httpx 的 `AsyncClient` **不接受同步流** |
| ③ **异步生成器 + 显式 `Content-Length` 头** | ✅ `262144` | ❌ 无 | ✅ **同时满足"流式"与"带长度"** |

实测输出（逐字）：
```
[① 异步生成器]                       Content-Length = (无)      Transfer-Enc = chunked
[② 文件对象]                         抛异常: RuntimeError: Attempted to send an sync request with an AsyncClient instance.
[③ 异步生成器 + 显式 Content-Length]  Content-Length = 262144   Transfer-Enc = (无)
```

**结论（这是本方案的技术基石）：**

> **方案③ 就是我们要的**：用**异步生成器**按 64 KB 分块读取加密后的临时文件，
> 同时**显式**在 headers 里写 `Content-Length: <密文字节数>`。
> httpx 不会追加 `chunked`，CDN 拿到的是合法长度 + 流式传输。
> 内存占用从 **278 MB 降到 64 KB**。

**顺带排除了两条死路**（记下来，免得以后有人再试）：
- 不能用文件对象 —— `AsyncClient` 直接拒收同步流；
- 不能用裸异步生成器 —— 会退化成 `chunked`，CDN 回 500。

**密文字节数从哪来？** 现成的：`media.py` 里已经算过 `ciphertext_length = encrypted_path.stat().st_size`（它还被发给了 `getuploadurl` 当 `filesize`），直接复用即可，无需多一次 IO。

**剩余的不确定项**（只能真机回答，见附录 C）：
- 278 MB 这个量级，CDN 究竟收不收？
- 收的话，需要多长时间？现有 45 秒读超时够不够？

---

#### 2.2.4 一句话总结这条问题

> **代码侧：整块上传是唯一的非流式环节，方案已实测可行，改造成本低。**
> **平台侧：出站上限未知且无错误码，278 MB 是入站官方上限的 2.8 倍 —— 所以必须"先探测、再定阈值"，并且要为"平台确实不收"准备降级路径。**

**代码原文（`core/office_tools.py`，注释是它自己写的）：**

    """...

    companion._notify_file_delivery({"path": str(target), "note": str(note or "")})

**投递端（`core/companion.py::_send_to_ilink`）把失败吞在这里：**

for path in list(getattr(reply, "file_paths", None) or []):

- `core/response_validator.py`：只查空回复

我用日志核实过：本次**没有**出现 `skip empty reply`，说明这次 `note` 非空、文件确实进了队列（所以才走到超时）。**但"只发文件、不带 note"这条路目前是静默丢件的**，只是这次没踩到。

### 2.4 【P1】路径授权：两个"根"错位 + 越界错误缺 `reason`

**配置现状（互相打架）：**
```yaml
agent.workspace_default_roots: [D:\AerieOffice]   # 工作区根（可读写）
office.dir: F:\文件\Aerie                          # 办公目录（文档落这里）
```

**Agent 第一次调用失败的原因**（13:15:49）：
```
send_file_to_user → fail  error=文件不存在或不在允许发送的目录内: D:\Harness创客工坊\Harness社团走班.pptx
```
文件**确实存在**（我实测 278 MB），失败是因为**`D:\Harness创客工坊` 当时还不是工作区根**。它在 13:16:20 才被自动加入、13:18:30 才被激活 —— 也就是说，**是失败之后才补上的授权**。

**这里有两个设计问题：**

1. **越界错误没带 `reason` 键**：
   ```python
   return {"success": False, "error": f"文件不存在或不在允许发送的目录内: {filepath}"}
   ```
   而授权桥 `core/write_approval.py` 只在 `result.get("reason") == "outside_workspace_roots"` 时才弹审批、加根、重试。
   → **`send_file_to_user` 越界时不会触发任何授权流程**，直接失败。（对比 `guard_write_paths` 是带 `reason` 的，两条写路径的语义在这里分裂了。）

2. **用户给"文件路径"无法授权**：`pipeline._extract_paths` 会提取 `盘符:\...` 并 `add_root`，但 `WorkspaceManager.add_root` 要求目标 `is_dir()`。你给的是 `D:\Harness创客工坊`（目录，能授权）——**但如果你给的是文件路径，就授权不了**。

**这条直接解释了"他一开始想从默认文件夹里找"**：办公目录在 F 盘、工作区根在 D 盘、提示词的 L5 方法论又教它"先 `file_search` 找文件"，三者叠加，Agent 自然先去翻默认目录。

## 五、修复方案（修缮报告）

### 5.1 修复原则

1. **先修"会放大伤害"的**：序列化 Bug 必须最先修，因为它让每一次失误都变成"上下文全废"。
2. **让失败可见**：任何投递失败都必须能回到模型，否则"假成功"无法根除。
3. **不做"以后再说"的临时方案**：工具返回值契约要一次性收口，不能只给 `shell_execute` 打补丁。
4. **大文件单独治**：278 MB 不该走"读进内存整块 POST"这条路。

### 5.2 P0 修复项

#### P0-1 · 工具返回值统一序列化归一化（修 §2.1）

**根因**：Observation 契约缺失 —— 工具可以返回任意 Python 对象，序列化在下游裸奔。

**改法（推荐：在契约层收口，而不是逐个工具改）**：

- 在 `core/tool_registry.py::execute` 出口做**唯一一次归一化**：
  - 已是 `dict/list/str/int/float/bool/None` → 原样通过；
  - 有 `to_dict()` 的对象（`ControlResult` / `AuditLogEntry` 都有）→ 调它；
  - `dataclasses.is_dataclass` → `dataclasses.asdict()`；
  - 其他 → `{"error": "tool returned non-serializable value", "type": ...}`（**必须让模型看得见**，而不是静默）；
- 在 `core/llm_caller.py` 组装 `tool` 消息处加**兜底**：`json.dumps` 失败时退化为 `{"error": ...}` 文本，**绝不让异常打断 `working_msgs` 的配对完整性**；
- 在同一个 `for tc in new_calls` 循环里加 `try/finally` 保证：**只要 append 了 assistant tool_calls，就必须为每个 `tc_id` append 一条 `tool` 消息**（哪怕内容是错误占位）。这是 OpenAI 兼容接口的硬约束。

**为什么这样改**：这三处是同一个契约的三个面（产出 / 消费 / 配对）。只修一处，另外两处迟早再犯。

**验收标准**：
- 新增单测：注册一个返回裸 `ControlResult` 的假工具 → ReAct 循环不抛异常、`tool` 消息存在、`json.dumps(working_msgs)` 成功；
- 新增单测：工具抛异常时，`working_msgs` 中 assistant tool_calls 与 tool 消息**数量配对**；
- 回归：`system_control` 12 个工具逐个跑一次，`tool_call_log` 无 `TypeError`。

**风险**：低。归一化只加一层类型转换，不改变工具语义。

---

#### P0-2 · 投递失败必须回到模型（修 §2.3）

**根因**：工具返回"已入队"被模型理解为"已完成"；真实失败只进日志。

**改法**：
1. **工具语义分层**：`send_file_to_user` 的返回从 `{"success": True, "queued": True}` 改为 **`{"status": "queued", "note": "已提交投递队列，送达结果稍后回报"}`** —— 明确"未完成"，不再用 `success: True` 这个词；
2. **失败回灌**：`_send_to_ilink` / `_send_to_qq` 的 `except` 里，把失败**写进会话**（一条系统级 `tool` 结果补充，或一条 assistant 可见的"附注"），让下一轮模型知道"上次那个文件其实没发出去"；
3. **口径统一**：把"投递结果"做成一个可查询的状态（`delivery_id` → `pending/sent/failed`），模型可主动查；这是根治，但工作量较大，可作为 P1。

**验收标准**：
- 单测：文件发送抛异常 → 模型下一轮上下文里能看到该失败；
- 手工：微信发一个超限大文件 → Agent 不再说"已经发过去了"，而是说"太大了没发出去"。

**风险**：中。改了工具返回结构，需同步检查是否有下游按 `success` 字段判断。

---

#### P0-3 · 大文件投递：**改造为流式上传**（修 §2.2）— 用户决策：**要能发出去**

**根因**：278 MB × `read_bytes()` 整块入内存 × 45s 读超时 × 出站上限未知。

**用户决策（2026-09-28）**：**选 A —— 大文件要能发出去。** 不是"快速失败"。

---

##### 步骤 1 · 先探测真实阈值（**必须先做，不能跳过**）

**为什么必须探测**：§2.2.2 已确认出站**没有任何公开上限**，也没有可捕获的错误码。
所以"阈值"这个数字**不能靠猜、不能抄第三方博客**（那些数字都是各实现自己加的保险值）。
唯一可靠的办法：**本机用真 bot_token 从 1 MiB 起二分调大，记录第一个失败点。** 脚本见**附录 C**。

**产出**：一份真实阈值表（各档位的成功/失败 + 错误形态），据此确定：
- 我们的**安全上限**（建议取实测阈值的 60~70%，留余量）；
- 278 MB 是否在可达范围内 —— **这决定后面是走"流式上传"还是"降级路径"**。

**这一步不改任何代码**，只跑脚本、收数据。

---

##### 步骤 2 · 流式上传（方案已实测可行，见 §2.2.3）

> **R5 状态（2026-09-28）**：已实现，但**默认关闭**（`ilink.media_upload_streaming: false`），
> 生产仍走已真机验证的整块路径。原因是两处证据**不在同一个可信层级**：
>
> | 证据 | 强度 | 结论 |
> |---|---|---|
> | §2.2.3 的 httpx 对照（显式 Content-Length，无 chunked） | **弱** —— `MockTransport` 不做真实 HTTP 分帧，"无 chunked"是 httpx 内部对象状态，不等于线上如此 | 写法在库层面成立 |
> | `communication/ilink/media.py` 的真机注释（2026-09-28） | **强** —— 同一 URL 整块 200、流式 500，是真的打到了 CDN | 线上拒绝了流式 |
>
> 弱证据不能推翻强证据，所以不拿生产去赌：开关打开即走分块 + 显式 `Content-Length`，
> **跑一次真机就能给出确定结论**（顺带验证 278 MB 是否需要整个进内存）。这与 §6.4
> 回退表里"保留整块路径的开关"是同一条要求。

**改 `communication/ilink/media.py::upload` 的最后一公里**：

| 现状 | 改为 |
|------|------|
| `ciphertext = encrypted_path.read_bytes()`<br>`await self._http_client.post(upload_url, content=ciphertext, headers={...})` | 用**异步生成器**按 64 KB 分块读取 `encrypted_path`<br>+ **显式** `headers={"Content-Length": str(ciphertext_length), "Content-Type": "application/octet-stream"}` |

**为什么是这个写法**（本机实测，见 §2.2.3 对照表）：
- 只传异步生成器 → httpx 给 `Transfer-Encoding: chunked` → **CDN 回 500**；
- 传文件对象 → `AsyncClient` 抛 `RuntimeError`（**不接受同步流**）；
- **异步生成器 + 显式 Content-Length → 两者兼得**（实测 `Content-Length: 262144`、无 chunked）。

**顺带收益**：内存峰值 **278 MB → 64 KB**；配合 P0-2 的失败回灌，失败也能说清原因。

**注意加密侧不用动**：`media_crypto.py::encrypt_media` 已经是 64 KB 分块流式，唯一的非流式点就是 `read_bytes()`。
（"磁盘双写"这条技术债本轮**不动** —— 临时密文文件是必要的，因为要先知道 `filesize` 才能换 `getuploadurl`；动它属于优化，不是修 Bug。）

---

##### 步骤 3 · 上传专用超时（与步骤 2 同批改）

`ILinkClient.DEFAULT_TIMEOUT` 的 `read=45` 对 278 MB 量级明显不够。
- 给**媒体上传这一次 POST** 单独传一个宽松超时（如 `connect=10, read=180, write=180, pool=10`），
  **不要**直接放宽全局 `DEFAULT_TIMEOUT`（那会让文本通道的失败检测变钝）；
- 加**进度日志**（每 N MB 记一次已发送字节），便于区分"在慢慢传"和"卡死了"。

> **R5 已落地**：上传 POST 单独传 `read/write = ilink.media_upload_timeout_sec`
> （默认 **300s**，比这里建议的 180 更宽，因为上限还没探测出来；探测完成后按实测收窄）。
> 上传前打一条 INFO：`ciphertext=xx.x MiB 超时=yyy s CDN=…`，用于和探测脚本的数据对齐。
> 逐步进度日志**暂不做** —— 先有阈值再谈观测密度。

---

##### 步骤 4 · 兜底降级（仅当步骤 1 证明平台确实不收时启用）

如果实测显示 CDN 在某个尺寸之上**稳定失败**，那么"能发出去"只能靠**换通道**。按优先级：

| 方案 | 做法 | 适用 |
|------|------|------|
| **A. 云端链接** | 上传到可直链的存储（或本地 HTTP 服务内网地址），把**链接**发给用户 | 用户能点开链接 |
| **B. 分卷** | 拆成多个 < 阈值的分卷依次发送（`.part1/.part2`）+ 一个合并说明 | 用户愿意动手合并 |
| **C. 换通道** | 微信超限 → 自动改走 QQ（或反向） | 另一通道在线 |
| **D. 明确告知** | 都不行时，如实说"这个文件 278MB，超过通道能力"，**禁止说"已经发过去了"** | 最后的诚实底线 |

**D 是底线，不可省略** —— 它是 §2.3"假成功"的直接解药。

---

**验收标准**：
- 步骤 1：拿到真实阈值表（含 278 MB 那一档的结论）；
- 步骤 2：单测 —— **断言发出的请求带 `Content-Length` 且不含 `Transfer-Encoding`**；断言内存不随文件增长（用 100 MB 假文件跑，峰值内存可控）；
- 步骤 3：单测 —— 媒体上传用的是专用超时，不是全局 45s；
- 端到端：**真机发 278 MB 那份 PPT，用户确认收到**（或按步骤 1 结论走降级，且**Agent 说的话与实际一致**）。

**风险**：
- 步骤 1：零风险（只读探测）；
- 步骤 2：**中等** —— CDN 对传输编码敏感，必须真机验证；若失败，回退到原整块方案（保留开关）；
- 步骤 3：低；
- 步骤 4：中等（新链路，需单独设计）。

**必须说清的一件事**：如果步骤 1 的结论是"278 MB 超出平台能力"，那么**任何客户端代码都改不出"能发出去"**。
届时我会带着实测数据回来找你，再定走 A/B/C/D 哪条 —— **而不是硬扛着上传、让它 47 秒后超时、然后 Agent 继续编"已经发过去了"。**

## 附录 C · iLink 出站体积梯度探测脚本（待跑）

**目的**：出站上限无公开数字、失败无错误码（§2.2.2），所以只能靠实测定位第一个失败点。

**脚本要做的**：用真 `bot_token` + 真 `to_user_id`，按梯度生成假文件 → 走**与生产完全相同的** `getuploadurl` → CDN 上传 → `sendmessage` 链路，
记录每一档的 `getuploadurl` 返回、CDN 的 HTTP 状态、耗时，以及**失败时的错误形态**（超时 / 4xx / 5xx / 静默）。

**放在哪**：建议 `scripts/probe_ilink_upload_size.py`（一次性诊断工具，不入主链路）。

**骨架**（需要你确认后再落地；此处只给设计，不含真实凭据）：

```python
"""iLink 出站体积梯度探测 —— 定位第一个失败的档位。

用法：
    python scripts/probe_ilink_upload_size.py --to-user <wx_id> --sizes 1,5,10,25,50,100,200,278

凭据来源（不落盘、不进日志）：
    data/ilink_credentials.json（与生产同一份），或 --token/--base-url 显式传入
"""
import argparse, asyncio, hashlib, os, secrets, tempfile, time
from pathlib import Path

import httpx

from communication.ilink.client import ILinkClient
from communication.ilink.media import ILinkMediaTransfer
from communication.ilink.models import MediaType
from core.ilink_credentials import ILinkCredentialsStore


async def probe_one(client, transfer, to_user, size_mib: float, context_token: str):
    """跑一档：造文件 -> 加密 -> getuploadurl -> CDN 上传 -> 发消息。"""
    size = int(size_mib * 1024 * 1024)
    path = Path(tempfile.mkstemp(suffix=".bin")[1])
    path.write_bytes(secrets.token_bytes(min(size, 1 << 20)) * max(1, size >> 20))
    row = {"size_mib": size_mib, "actual_bytes": path.stat().st_size}
    t0 = time.monotonic()
    try:
        media = await transfer.upload(
            client, path, to_user_id=to_user, media_type=MediaType.FILE
        )
        row["getuploadurl"] = "ok"
        row["ciphertext_bytes"] = media.ciphertext_length
        row["elapsed_sec"] = round(time.monotonic() - t0, 1)
        # 只记录"能上传到 CDN"，不发消息给用户（避免刷屏）
        row["result"] = "UPLOAD_OK"
    except httpx.ReadTimeout:
        row["result"] = "READ_TIMEOUT"
        row["elapsed_sec"] = round(time.monotonic() - t0, 1)
    except httpx.HTTPStatusError as exc:
        row["result"] = f"HTTP_{exc.response.status_code}"
        row["elapsed_sec"] = round(time.monotonic() - t0, 1)
    except Exception as exc:  # noqa: BLE001
        row["result"] = f"{type(exc).__name__}: {exc}"
        row["elapsed_sec"] = round(time.monotonic() - t0, 1)
    finally:
        path.unlink(missing_ok=True)
    return row


async def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--to-user", required=True, help="接收方 wx id（from_user_id）")
    ap.add_argument("--sizes", default="1,5,10,25,50,100,200,278")
    ap.add_argument("--timeout", type=float, default=300.0, help="单档读超时（秒）")
    args = ap.parse_args()

    creds = ILinkCredentialsStore().load()
    assert creds is not None, "未找到 iLink 凭据，请先在应用内完成扫码登录"
    # 探测用**宽松超时**，避免把"慢"误判成"不支持"（生产超时另议）
    timeout = httpx.Timeout(connect=10.0, read=args.timeout, write=args.timeout, pool=10.0)
    async with httpx.AsyncClient(timeout=timeout) as http:
        client = ILinkClient(creds.base_url, creds.bot_token, http)
        transfer = ILinkMediaTransfer(http, "data/ilink_media_probe")
        rows = []
        for s in (float(x) for x in args.sizes.split(",")):
            row = await probe_one(client, transfer, args.to_user, s, "")
            rows.append(row)
            print(row, flush=True)
        print("\n=== 汇总 ===")
        for r in rows:
            print(f"{r['size_mib']:>7} MiB  {r['result']:<22} {r.get('elapsed_sec','')}s")


asyncio.run(main())
```

**跑完要看的三件事**：
1. **第一个失败档位在哪** → 这就是"安全上限"的锚点（建议取它的 60~70%）；
2. **失败形态是超时还是 HTTP 错误** → 决定 P0-3 是"加超时"还是"换降级路径"；
3. **成功档位的耗时曲线** → 决定生产侧媒体上传超时该设多少（步骤 3）。

**注意**：
- 脚本**只上传到 CDN，不发送消息**，所以不会往你微信里刷一堆测试文件；
- 但 `getuploadurl` 与 CDN 上传**会真实消耗配额**，这是无法避免的（也正是必须实测的原因）；
- 脚本用**宽松超时**（默认 300s），因为探测的目的是"找出平台能力边界"，不是"复现生产超时"。

### 8.1 需求原文与目标

### 8.3 分级规则：按「画面信息量」四档

**核心思路**：不按"谁最重要"分，而按**画面里有多少信息要模型同时处理**分。
人像是**单主体中等信息量**；小部件是**低信息量**；场景/海报是**高信息量**。

| 档 | 名称 | 模型 | 典型分辨率 | 触发信号 |
|---|---|---|---|---|

| **T3** | 人像·写真感 | 美学 V8.2 | 1K~2K | 人像类 且 `style ∈ {氛围感, 诱惑感, 慵懒}`（"情绪片 / 写真感"诉求） |
| **T4** | 低信息量·小部件 | Lite | 2K（需要细节用 4K） | ① `focus ∈ _CLOSEUP_FOCUS_SET`（手/腿/脚/腰/肩颈/背影/头发/脸/眼睛等**局部特写**）<br>② 无人物的小物件 + `shot ∈ {特写, 大特写}` |

**判定优先级（从高到低，先命中先定）**：

```
1. 用户显式指定（海报/封面/设计）        → T1   ← 用户意图优先，压倒一切

4. 人像 + 写真感风格                      → T3
5. 人像（其余）                           → T2

```

### 8.5 失败降级链（**不能因为省钱就让用户拿不到图**）

  之后直接转中转（中转是包额度口径，不额外烧即梦积分）；
- 与既有 `image_edit_v1` 的降级护栏语义保持一致（`core/world_image_candidates.py::_generate_workflow_result`）。

## 九、【R3 新增】三端按「来源端口」投递

### 9.1 需求原文

> "支持把这个产出的文件发到对应的端口上去，比如**我在桌面端要能发到桌面端，我在 QQ 端要发到 QQ 端，
> 我在微信端要发到微信端**。"

**语义**：**回请求的来源端口** —— 而不是"最近入站通道"，也不是"QQ 优先"。

---

### 9.2 现状：三处实现与需求不一致（代码事实）

| # | 位置 | 现状 | 问题 |
|---|---|---|---|
| **①** | `core/companion.py:3179` | `_last_inbound_target` **只在 `msg.source in {"qq","ilink"}` 时记录** | **桌面端发起的请求根本不进这个记录** |
| **②** | `core/companion.py:2901-2904`（`_notify_file_delivery`）<br>`core/companion.py:2876-2881`（`_notify_pending_approval`） | 用**全局** `_last_inbound_target` 决定投给谁；取不到直接 `return` | 桌面端要文件 → 投到**上一次** QQ/微信通道；若从未有 QQ/微信入站 → **静默丢件**（只写一行日志） |
| **③** | `core/companion.py:3977`（主动发图循环）<br>亦见 `:3605`、`:5294` | `channel = "qq" if self.qq.is_logged_in else "local_chat"` | **只要 QQ 在线就永远投 QQ** —— 完全忽略用户实际在哪一端 |

**对照组（证明正确模式已经存在，只是没被复用）**：
`core/pipeline.py:1370-1372` 聊天要图**已经**按来源通道回投：

```python

```

→ **结论：不是缺能力，是缺"统一语境"。** 图片候选（`world_image_candidates`）里的
`channel` 是对的；坏的是**文件投递与主动消息**这两条走了全局状态。

### 9.3 设计：请求级投递上下文（DeliveryContext）

**核心**：把"这条请求从哪来"变成**请求级**数据，随请求贯穿到工具执行与投递端，
而不是读一个全局的"最后一次入站"。

```python
@dataclass(frozen=True)
class DeliveryContext:
    channel: str              # qq | ilink | local_chat
    user_id: int
    channel_account_id: str = ""
    turn_id: str = ""         # 关联到本轮对话，便于审计
```

**接线点**：

| 位置 | 改动 |
|---|---|
| 入站（`_submit_incoming_message`） | 构造 `DeliveryContext` 并**存进请求上下文**（`request_context` / `IncomingMessage`），**桌面端也记** |
| 工具执行期 | `tool_send_file_to_user` / 审批回调从**当前请求上下文**取 origin，而不是 `_last_inbound_target` |
| `_notify_file_delivery` / `_notify_pending_approval` | 优先用请求级 origin；**取不到才回落**全局 last-inbound（保留向后兼容的兜底，但不再是主路径） |
| 取不到 origin 时 | **不再静默 return** —— 落桌面端可见 + 明确告知模型"无法确定投递端口"（与 P0-2 合流） |

**为什么用请求级而不是修全局**：全局 `_last_inbound_target` 在**多端并发**时必然错乱
（你在桌面问、同时手机 QQ 来一条推送 → 文件就投错端）。这是结构问题，打补丁治不好。

---

### 9.4 主动消息（无 origin）的端口策略

主动发图 / 主动推送**没有"来源端口"**（不是用户请求触发的），必须显式定义策略。

**建议**（配置项，默认 `auto`）：
```yaml
proactive:
  primary_channel: auto          # auto | qq | ilink | desktop
  auto_recent_window_min: 30     # auto 模式下"最近活跃端口"的有效期
```

> **R4 落地修正（2026-09-28）**：这里原本建议新造一个 `delivery_channel` 键，实现时发现
> `proactive.primary_channel` **早就存在**（electron 的「外部连接」面板就在写它，而 Python
> 侧自某次改动后不再读 → 那个设置"看得见但不生效"）。两个键表同一件事 = 两个真源，
> 所以最终**复用 `primary_channel`** 并给它加上 `auto` 取值（别名 desktop/local → local_chat，
> wechat → ilink；未知值按 `auto`）。面板的设置由此重新生效。

- `auto`：投给**最近一次用户活跃端口（含桌面）**，且需在时间窗内；
  窗口内无活跃记录 → **落桌面端**（最保守、一定能看到，不会打扰手机）；
- 指定端口：固定投该端口（用户明确要"主动消息都发我微信"时用）。

**同时修掉 ③**：把 `"qq" if qq.is_logged_in else "local_chat"` 换成
`resolve_proactive_channel()`，语义集中在 `image_tiering` 同级的新模块或
`core/delivery_routing.py`（**唯一真源**，避免五个调用点各写一遍）。

| 15:55:51 | 发图 `6870d9a8da944ad7987050fce7adbbbc.png` —— **画面是在家里、窗边、有城市江景** |

→ **文字说在步行街（室外），图是家里窗边（室内）。**

---

### 10.2 根因：一条四层断链（代码级，全部本机核实）

#### ① 场景池选场景时**完全不看世界地点**

`core/companion.py:4291-4292`：
```python
topic_text = str((candidate or {}).get("user_raw") or "")
scene = select_scene(topic_text)      # ← 只传了话题文本
```

而 `core/image_scene_pool.py::select_scene(topic_text, region, rng)` 的 `region` 参数
**没有被传入** → 永远用 `default_region`（= `chongqing`），
**世界快照里的真实地点（步行街）根本没进入这个决策**。

更关键：即使传了 `region`，**也没有"室内/室外"这个约束维度** ——
`select_scene` 的采样范围是 `list_scenes()` = **indoor + outdoor 全摊平**。

#### ② 关键词表不覆盖，导致"零亲和 + 纯随机"

- 实配场景池：`config/image_scenes.yaml`（7.8 KB），**indoor 18 个 + outdoor 14 个**，地理分组只有 `chongqing`；
- 采样是 `softmax(weight / temperature)`：命中关键词才把权重 × `affinity_boost`(2.5)，
  **任何场景概率都不为 0**（设计如此，见模块 docstring）；
- **"步行街"三个字不在任何场景的关键词里**：
  - `hongyadong_street` 的 kw 是 `['风情街','洪崖洞','坡坎']`
  - `street_stroll` 的 kw 是 `['散步','逛街','街头']` —— **"步行街"不含"逛街"也不含"街头"**（子串不匹配）

**本机实测**（同一句话题，采样 100 次）：
```
topic = "一抬头发现自己在步行街站了半小时 你说我是不是该找个地方坐坐 不对 我是想问你有空了吗"
group distribution over 100 draws: {'indoor': 55, 'outdoor': 45}

scene_weights(topic) == scene_weights('')  →  True    # 无任何关键词命中 = 纯随机
```

> **即：这句话配图时，有 55% 的概率被配成室内。这次就命中了那 55%。**

#### ③ 选中的场景被**硬拼进基础提示词**

`core/companion.py:4298-4300`（场景池钩子）+
`core/companion.py:4492-4494`（`_compose_base_image_prompt` 内）：
```python
scene_prompt = str((candidate or {}).get("scene_prompt") or "").strip()
if scene_prompt:
    merged = f"{merged}{scene_prompt}。{_LIFE_SNAP_STYLE_PHRASE}"
```
→ 场景池产出的**具体画面描述**（如"她窝在沙发上看剧，屏幕的光映在脸上"）
被**直接追加**到基础提示词末尾。**画面在此时已被锁死为室内。**

#### ④ 世界数据接力**在场景之后**才跑，且被明令"只增强、不推翻"

`core/companion.py` 的执行顺序（**这是问题核心**）：
```
4287-4296  场景池选场景  →  spec["scene"] / candidate["scene_prompt"]
4301       base = _compose_base_image_prompt(...)     ← 场景已被写进 base
4305       context = self._image_world_context(...)   ← 世界地点（含 outdoor）在这里才出现
4309       refined = await self._light_relay_refine_prompt(base, context, ...)
```

而接力用的 system prompt（`core/companion.py:4690`）明确要求：
> "3. **保留**基础提示词里的人物外貌、身材、风格与**构图**信息，只做上下文增强；"

→ **接力被要求保留 base**，而 base 里已经写着"窝在沙发上看剧"。
世界数据说"她在室外"、base 说"她在沙发" —— **两条互相矛盾的指令，
而其中一条（base）被明文保护。结果必然是室内场景胜出。**

#### ⑤ 确定性兜底**从不注入地点**

`core/companion.py::_inject_world_context_fallback` 只注入三类：
`light`（时间光线）/ `room`（房间物件）/ `weather`（天气）——
**没有 location**。所以"轻量 LLM 接力不可用"时，地点矛盾**完全没有兜底纠正**。

---

### 10.3 最扎心的一点：**系统其实「知道」她在步行街**

不是数据缺失，是**信息用晚了**。以下代码证明世界数据早就备好了：

| 位置 | 内容 |
|---|---|
| `core/companion.py:4595` | `"outdoor": bool(snapshot.get("outdoor"))` —— **已判定她在室外** |
| `core/companion.py:4596` | `"outdoor_place": str(snapshot.get("outdoor_place") or "")` —— **已有具体地点** |
| `core/companion.py:4648-4650` | `_world_context_text()` 甚至**逐字写出了**：<br>`"状态：她此刻在室外（步行街），不在家里。"` |
| `core/companion.py:4748` | 确定性兜底里也有 `if context.get("outdoor")` 的分支（把"房间物件"改述成"身边地点"） |

**这些全部发生在场景池选完之后约 300 行处** ——
→ **信息存在、判定正确、甚至已经写成了自然语言，但它无法影响已经选定的场景。**

> 一句话根因：**场景池是一个"与世隔绝的随机数生成器" —— 它知道话题关键词，
> 但不知道她此刻在世界里的真实位置；而唯一知道位置的模块，被安排在它之后，且无权否决它。**

### 10.4 影响面（不止这一例）

| # | 影响 | 说明 |
|---|---|---|
| 1 | **所有"人在室外"的人物配图，约 55% 概率被配成室内** | 反向亦然：人在家里可能被配成"江边散步" |
| 2 | 主动配图（`_maybe_attach_companion_image`）与主动发图（`_proactive_photo_loop`）**都走这条路** | 都是人物类 `prompt_key` → 都过场景池 |
| 3 | **与 §八 分级路由产生交互** | 场景判断错误 → 档位判断也会错（人在室外算"大场景"应走 T1，却被当室内人像走 T2） |
| 4 | 与 §九 多端口投递叠加 | 图文不一致会在三端同时呈现（这次就是桌面端） |
| 5 | 用户感知为"**她在演戏**" | 世界观一致性是产品差异化核心（见 §4.3），图文矛盾直接损伤它 |

### 10.5 修复方案

**核心思路：把「世界地点」从"最后才参与的补充信息"提升为"选场景时的硬约束"。**

#### 步骤 1 · 调整执行顺序（**这是必须的一步**）

```
改前：选场景 → 拼 base → 取世界上下文 → 光线接力（只增强）
改后：取世界上下文 → 用(outdoor/place)约束选场景 → 拼 base → 光线接力
```

即把 `_image_world_context(candidate)` **上移到场景池钩子之前**。
它是纯读取（读 world snapshot + 时间兜底），**没有副作用，上移零风险**。

#### 步骤 2 · 给场景池加"室内/室外"硬约束

`core/image_scene_pool.py`：

```python
def select_scene(
    topic_text: str = "",
    region: str = "",
    outdoor: bool | None = None,   # ← 新增：世界地点约束（None = 不约束）
    rng: Callable[[], float] | None = None,
) -> dict[str, Any]:
    """... outdoor 为 True/False 时**只在对应分组内采样**，不再跨组。"""
```

- `outdoor=True` → 只在 `load_regions()["outdoor"]` 内采样；
- `outdoor=False` → 只在 `indoor` 内采样；
- `outdoor=None` → 保持现状（全摊平），兼容"world 关闭/无快照"的场景；
- **默认硬过滤**（不是加权）—— 因为"人在室外却配室内"属于**事实错误**，
  不是风格偏好，不能用概率去赌；
- **一个总开关**：`config/image_scenes.yaml::respect_world_location`（默认 `true`）。
  设为 `false` 即恢复"全摊平"采样（= 当前行为），留作回退与创意场景的余地
  （硬过滤 vs 软加权的取舍见 §七-10）。

#### 步骤 3 · `region` 由世界快照的 city 推导

把 `select_scene(topic_text, region=city_from_snapshot, outdoor=...)` 的 `region`
接上世界快照的 `city`，让"未来加地域 = 只加 yaml 分组"的设计真正生效。

#### 步骤 4 · 关键词表补齐（让亲和度真正生效）

在 `config/image_scenes.yaml` 补常见室外/地点词：
- `hongyadong_street`: 补 `步行街`、`商业街`、`广场`、`商圈`
- `street_stroll`: 补 `逛街`、`压马路`、`街边`
- 建议同时加一条**兜底规则**：话题里出现"街/路/广场/公园/商场"等**地点类字**时，
  即使没命中具体场景，也**提升整个 outdoor 组的权重**（组级亲和），
  避免"词不达意 → 零亲和 → 纯随机"。

#### 步骤 5 · 接力指令给"地点"一票否决权

`_light_relay_refine_prompt` 的 system prompt 第 3 条从
"保留基础提示词里的人物外貌、身材、风格与**构图**信息"改为：

> "保留基础提示词里的人物**外貌、身材、风格**信息；
> **但若世界背景数据表明她此刻在室外（或指定地点），而基础提示词描述的是室内场景，
> 必须按世界数据改写场景——世界地点优先级高于基础提示词里的场景描述。**"

#### 步骤 6 · 确定性兜底补 location

`_inject_world_context_fallback` 增加 `location` 注入分支
（室外 → "她此刻在{outdoor_place}"；室内 → 保留房间描述），
使"轻量 LLM 不可用"时也不会出现图文矛盾。

#### 步骤 7 · 可观测

每次生图在既有 `[WorldPrompt]` 日志上追加：
```
[WorldPrompt] scene_id=… group=indoor/outdoor outdoor=True place=步行街 corrected_by_world=True/False
```
`corrected_by_world` 用于量化"有多少次场景被世界数据纠正"，
作为步骤 1~5 的疗效指标。

| 风险 | 应对 |
|---|---|
| 硬过滤让画面变单调（室外永远只出室外） | 这是**正确的单调**（事实一致性优先）；且分组内已有 18/14 个场景，够用 |

→ 场景池恢复"全摊平"采样，即当前行为。

### 10.9 【R4 二次复盘】首轮修完之后，用真实方法复现仍发现 4 个残留（已全部修掉）

首轮修复只把世界地点传给了**场景池**。R4 改用**真实方法链路**（不桩 base / 光照 /
兜底，只桩 world 快照与轻量 LLM）复现同一句话，暴露出 4 个残留 —— 前两个是
"同一条提示词里自相矛盾"，第三个正是用户截图里那个矛盾的**直接来源**：

| # | 残留 | 证据（修复前实测） | 修法 |
|---|---|---|---|
| ① | **普通闲聊被切成"部位特写"**（跨词误命中） | 提示词出现"画面重点聚焦在**头发**，85mm 特写"——因为"一抬**头发**现在步行街"里 `抬头发现` 含「头发」；另"找个地**方**坐坐"让整图被判成**方图** | `_keyword_hits` + 两张**登记制**守卫表（裸单字需语境、跨词词禁邻字），方向表去掉单字 |
| ② | **方图被谎报成"横构图 16:9"** | `orientation_phrase` 用 `width >= height`，1024x1024 也输出"横构图（手机横拍 16:9 比例）" → 提示词说的比例与真正传下去的 size 打架 | 增加方图分支（1:1 → 方构图） |
| ③ | **base 里写死的室内场景没让位** | 室外时提示词同时含"**她在家里的**随手自拍"（base）与"场景是风情街"（场景池） | `_compose_base_image_prompt` 读 `candidate["world_outdoor"]`，室外时改用户外措辞 |
| ④ | **太阳光措辞仍是室内的** | 室外时提示词出现"阳光直直洒进南偏东(SE)的**落地窗**，**窗外**是小区绿植" —— 直接推翻"她在步行街" | `solar_time.fine_time_descriptor(..., outdoor=)` 分流两套措辞（室外只写天光/街灯/夕阳） |
| ⑤ | **world 沉默 → 场景户外、光照室内**（自相矛盾） | 无快照时场景池能选到 outdoor（组级亲和），但光照仍是"洒进落地窗" | 新增**文本地点线索补位** `image_scene_pool.text_outdoor_hint` / `resolve_outdoor_hint`：world 优先，world 沉默则用话题地点词 |

**修复后实测（同一句话，真实方法链路）**：

```
A. world 说在室外（步行街）  → 场景 小区花园/风情街（outdoor，constrained=True）
                              提示词：她在步行街的随手自拍 … 午后的阳光直直照下来，影子清晰 …
                              室内措辞泄漏：无 ✅
B. 无 world 快照              → 场景 街边撸串（outdoor，constrained=True）
                              提示词：她在户外的随手自拍 … 暖橘色的夕阳落在建筑与江面上 …
                              室内措辞泄漏：无 ✅
C. world 说在家里（反向）      → 场景 窗前发呆（indoor）
                              提示词：她在家里的随手自拍 … 屋内暖灯亮着，窗外是…
                              未被户外化 ✅（world 是真源，闲聊里的"步行街"不翻盘）
```

**新增回归**：`test_world_location_prompt_consistency.py` 4 项（含"整条提示词不含
室内措辞"的收紧断言、文本线索补位、反向不户外化、光照两套措辞）；
`test_image_scene_pool_world_location.py` 3 项（地点线索单测）；
`test_modular_photo_prompt.py` 5 项（误命中守卫）。

## 十一、【R6 新增】世界状态外显 · 生图拍摄手法重构 · 语料内化

### 11.1 需求原文（用户，2026-09-28）

> ① "这个世界模拟相关的东西的话，我想让它不要在这一个地方里面藏着，而是把它作为一个显示的一个东西。
> 比如在每日日报这个展开之后可以看到它，或者是它那个灵动岛，它那个悬浮窗可以看到。"
>
> ② "生图的话，即梦的生图有点问题……我看出来他是想表达自拍的意思了，但是**不要出现任何的手机元素
> 或者是相机元素**，因为它这个本来是一个第一人称的视角去看它这个主体。……你可以让他写，比如说
> 使用 iPhone 的前置摄像头或 iPhone 的后置摄像头去拍摄，然后怎样怎样，有什么构图。……**硬组合的话，
> 只适用于场景和周围的景观**，但不太适合详细的怎么去生成。你可以**根据它不同的类型去配套相应的一些
> 拍摄手法**（惬意一点的就用比较温和柔和的镜头、构图、姿势）。"
>
> ③ "上面这个世界模拟里面，它那个**实时状态和它拍照的状态应该是一样的**。"
>
> ④ "**不要让他去根据 document 文件夹里面的那些文件去生成，而是把这些东西去提炼，然后内化到这个程序里面去。**"

### 11.2 根因（代码事实）

## 十二、【R7 新增】内置 QQ 运行时：消除 Beta QQ 风控 + 免 QQ 登录窗口

### 12.1 需求原文（用户，2026-09-28）

> "在这个项目开发的最初期，使用的是一个特殊版本的命令行输入的 QQ，在这个版本里面 NapCat 接入不会产生报错。
> 但是现在用的这个版本是最新版，它会有相应的防范，导致说连上一段时间之后，它那个账号会弹提示说账号有问题，
> 然后需要重新登录。也就是说，需要在此程序里面内置一个那个特殊版本的 QQ，然后跟目前的 NapCat 进行兼容，
> 这样只需要在程序里面进行扫码登录即可，**不用再弹出来一个 QQ 登录界面**。"

**用户决策（三问三答）**：① QQ 版本 → **用官方完整包内置的 QQ**；② 有头/无头 → **换无头绿色版**；
③ 交付方式 → **内置引导安装器**（"反正都可以下载下来，而且还可以让安装包更小一些，
只需要规定好下载的位置，以及保证它可以正常调用就可以"）。

### 12.2 诊断（本机实测事实，非推测）

| # | 事实 | 证据 |
|---|---|---|
| ① | 当前 NapCat 注入的是**系统安装的 Beta 通道 QQ** | 注册表 `UninstallString` → `D:\QQ_Beta\Uninstall.exe`；`D:\QQ_Beta\QQ.exe` 版本 **9.9.26.44343**；`versions/` 里已躺着升级包 `…-9.9.36-53644.zip` |
| ② | 启动器**只认注册表**，没有其他 QQ 来源 | `napcat_launcher._find_system_qq_exe()` 读 `HKLM\…\Uninstall\QQ` |
| ③ | NapCat 必须吃一个**外部 QQ.exe** | `napimain.exe <QQ.exe> <napiloader.dll> <nativeLoader.cjs>`；`data/napcat/` 里只有注入载荷（`QQNT.dll`/`wrapper.node`/`node.exe`），**递归搜不到 QQ.exe** |
| ④ | 官方引导器是 **GUI 程序**（无静默参数） | `NapCatInstaller.exe` 为 C++/MSVC（`CreateDirectoryW`、`std::filesystem`），反查 `--silent`/`/S`/`--help` 等开关**全部不存在** |
| ⑤ | 官方引导器的下载源可被我们**直接复用** | 二进制内含 `https://dldir1.qq.com/qqfile/qq/QQNT/be71d851/QQ9.9.26.44498_x64.exe`（腾讯官方 CDN，**非 Beta**）与 `NapCat.Shell.zip` 的 GitHub 多镜像 |
| ⑥ | 无头启动器存在且**可显式指定 QQ 路径** | OneKey 包内 `bootmain/NapCatWinBootMain.exe`；`launcher-user.bat` 的调用形态为 `<QQ.exe> <hook.dll> [QQ号]` —— 不需要注册表 |

**根因**：`_find_system_qq_exe()` 把"QQ 从哪来"交给了系统注册表 → 用户机器上是 Beta 通道 + 自动升级
→ 注入后账号被风控、频繁要求重新登录。**这不是 NapCat 的 bug，是 QQ 来源不可控。**

### 12.3 方案（主路径自动化 + 兜底内置引导器）

**① 受控 QQ 来源解析（收口风控根因）**
新增 `core/napcat_launcher.resolve_qq_exe(settings) -> (path, source)`，优先级：

1. **显式配置** — `AERIE_QQ_EXE` 环境变量 / `settings.napcat.qq_exe`；
2. **受控运行时目录** — `data/napcat-runtime/QQ/**/QQ.exe`（本方案主路径）；
3. **系统注册表（最后兜底）** — 保留可用性，但状态里**显式标注** `qq_source: system_registry`。

`get_status()` 新增 `qq_source` / `qq_ready` 两个字段 —— "当前吃的是哪份 QQ"从此**对用户可见**。

**② 受控安装（主路径，全程无 GUI）**
新增 `core/napcat_installer.py`：
- 下载**腾讯官方固定版本** QQ（`QQ9.9.26.44498_x64.exe`，**非 Beta**）到 `data/napcat-runtime/`；
- 静默安装（NSIS `/S /D=<dir>`）→ 失败改用**内置 7z 解包**（官方引导器同款手段）；
- 目标目录由配置决定（`AERIE_NAPCAT_RUNTIME_DIR` / `settings.napcat.runtime_dir` / `data/napcat-runtime`）；
- 阻塞操作全部由 API 经 `asyncio.to_thread` 调用，前端轮询进度。

**③ 兜底：内置官方引导器**
官方 OneKey 引导器（`NapCatInstaller.exe` + `bootmain/` + `7z`，合计 **约 2.2 MB**）落地到
`NapCat/OneKey/`，随 `extraResources` 打包（安装包只增加 2.2 MB）。需要人工介入时由面板一键拉起，
**工作目录固定为同一个受控目录**，避免它把东西装到不可预期的位置。

**④ 端到端串起来（不弹 QQ 客户端窗口）**
NapCat WebUI（6099）在无头下仍可访问 → 复用**已有的**二维码端点
（`/api/napcat/qrcode`、`/qrcode/refresh`、`/quick-login-list`、`/quick-login`），
扫码登录全程在 Aerie 内完成。

**⑤ 新增接口**

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/napcat/runtime/status` | 受控 QQ 运行时状态（含进度 / `qq_exe` / `installer_embedded`） |
| POST | `/api/napcat/runtime/install` | 后台线程安装受控 QQ（主路径） |
| POST | `/api/napcat/runtime/installer` | 在受控目录内拉起内置官方引导器（兜底） |

**⑥ 错误码细分**：`launcher_not_found`（缺 NapCat 本体）与 **`qq_not_found`**（缺 QQ 宿主）分开，
面板据此给可操作提示（"未安装受控 QQ 运行时"），而不是笼统的"启动器不可用"。

### 12.4 本轮已验证 vs 仍待真机验证

### 12.7 【R8 追加】真机验证暴露的问题与最终结论

上一轮落地后进入真机验证，暴露了 4 个必须修的问题。以下是**实测证据 + 最终结论**。

#### ① 【用户报告的阻塞项】启动 NapCat 会弹出 QQ 客户端窗口

用户原话："启动 Napcat 的同时把我电脑上面的原本有的 QQ 给打开了"。

**真机证据**：QQ 主进程 `MainWindowTitle="QQ"`、`MainWindowHandle≠0`（有窗口），
命令行是纯 `"D:\QQ_Beta\QQ.exe"` —— **不带 `--enable-logging`**。

**根因**：NapCat 有**两套启动器**，形态完全不同：

| 形态 | 启动器 | 行为 |
|---|---|---|
| **有头** | `napimain.exe <QQ.exe> <napiloader.dll> <nativeLoader.cjs>` | 注入后 QQ 的 GUI 进程**继续存活** → 窗口显示 |
| **无头** | `NapCatWinBootMain.exe <QQ.exe> <NapCatWinBootHook.dll>` | 注入后由 Hook **终止 QQ 的 GUI 主进程** → 无窗口 |

无头的判定证据是 `NapCatWinBootMain.exe` 二进制内的字符串：
**`[NapCat Backend] Terminate Main Process.`**
（另有 `--enable-logging` —— 这正是 `napcat.kill.qq.bat` 用来识别
NapCat 所启 QQ 的标记。）

而 `_build_launch_command` **只找 `napimain.exe`**，所以仓库自带的
`NapCat/NapCat.Shell`（完整无头部署：`NapCatWinBootMain.exe` +
`NapCatWinBootHook.dll` + `napcat.mjs` + `qqnt.json` + `loadNapCat.js`）
**从来没有被用上** —— 用的始终是下载器装的 `data/napcat`（有头）。

**真机验证（无头启动后的实测输出）**：
```
Boot Command:"D:\QQ_Beta\QQ.exe" --enable-logging
[NapCat Backend] Main Process ID:33292
config_current_version:9.9.26-44343          ← 与已装 QQ 匹配
[NapCat.Core] Version: 4.18.9
[WebUi] User Panel Url: http://127.0.0.1:6099/webui?token=...
可用于快速登录 of QQ：1. 3998874040 伊塔  2. 3489352115 伊泽
二维码已保存到 …\cache\qrcode.png
```
| 指标 | 结果 |
|---|---|
| **QQ 窗口** | 8 个进程**全部 `hasWindow=False`** ✅ 不再弹窗 |
| 程序自身启动 | `boot_mode=headless`、`phase=qr_pending`、`qrcode_available=true` |
| 二维码端点 | `GET /api/napcat/qrcode` → **HTTP 200, image/png** |

**结论**：无头形态可用，且**不需要额外"特殊版本 QQ"** —— `qqnt.json` 里的
`version` 与已装 QQ 的 `config_current_version` 各自独立，实测未冲突。

#### ② 受控 QQ 下载源两个都在真机上失效

| 地址 | 实测结果 |
|---|---|
| `dldir1.qq.com/.../be71d851/QQ9.9.26.44498_x64.exe`（官方引导器内置） | **404**（已失效） |
| `qqdl.gtimg.cn/qqfile/QQNTV2/9.9.36/.../QQ_9.9.36_260924_x86_01.exe`（当前官网直链） | **403**（防盗链；HEAD 与 Range GET 均不通） |

对照实验：同一网络下 GitHub 请求正常 → **不是本机网络问题，是腾讯 CDN 的访问策略**。

**结论**：程序内直连腾讯 CDN 下载**不可行**。改为**本地安装包优先**：
把"投递点"固定为 `<runtime>/installer`，用户用浏览器下载后放进去即可，
程序负责静默安装与目录收口（这才是"内置引导器 + 规定下载位置"的落地形态）。

#### ③ NapCat 永远起不来：`tasklist` 的 stdout 为 None

**真机日志**：
```

  File "core\napcat_launcher.py", line 475, in _spawn

**根因**：Electron 以 `stdio: ["ignore","pipe","pipe"]` 启动后端（stdin 无效），

PID 枚举只是看护辅助信息，**不该成为启动的阻塞点**。

> 在它之前，NapCat 一次都没真正启动成功过。

就会报 `launcher_not_found`。这轮把形态识别做成一等公民后，该目录才真正可用。

```

### 13.2 诊断（本机实测事实，非推测）

**① 桌面端图片没有附件 —— 落点是 QQ，桌面那条记录根本不是"图"。**

|---|---|---|---|

15:55 之前 QQ 未连上，走的只有 `local_chat` 分支（写附件）；QQ 连上后**只剩下 QQ
分支**在写历史，而 QQ 分支只写 `channel="qq"`、**不写 `attachments`**。

再往上追一层，找到"为什么只有 QQ 分支在跑"——**两层脱敏白名单都吃掉了
`delivery_channels`**：

* `core/world_port.py::redact_image_candidate`（in-process 世界端口）
* `world_service/storage/sqlite_store.py::_image_candidate_payload`（sidecar）

两者的 `public` 字典都是**显式白名单**，`delivery_channels`（多端口投递意图）与
`persona_id`（角色归属）都不在名单里 → 发布时被静默剥掉 → 消费端
`_candidate_from_event` 读到空列表 → 回落成"单一渠道"= `delivery_channels[0]` = `qq`。

**② 微信端一条主动消息都收不到 —— `_dispatch_push` 根本没有微信分支。**

`Companion._dispatch_push` 的 v2 投递只写了三条路：QQ 气泡 / 桌面 SSE / 系统通知。
`SendQueue` 早就注册了 `channel_senders={"ilink": self._send_to_ilink}`，`_send_to_ilink`
也早就实现（文本 + 文件），**能力齐备但主动推送这条路从未调用它**。

**③ 「后端离线」是重启竞态，不是后端真的死了。**

实测：后端 `22:40:15` 起、`/api/health` 返回 `status=healthy`、
`backend_instance_id=4bd5c002-…`、`data_path_id=e:\agent_reply\data\aerie.db`；
而 Electron（`22:31:57` 启动）一直显示「后端离线」。

根因在 `restartBackend()`：它在做 Electron 父级重启（`_forceRestartPythonBackend`：
杀子进程 → 重掷 `EXPECTED_BACKEND_INSTANCE_ID` → 用冷启动同一路径拉起）**之前**，
还"礼貌地"发了一次 `POST /api/system/restart`。那个端点会拉起
`tools/restart_helper.ps1`，helper 杀掉后端并以**孤儿进程**身份另起一个 main.py。

于是两个后端抢 7890：孤儿带着**旧** instance id，一旦它先绑上端口，
`healthCheck()` 里 `backend_instance_id !== EXPECTED_BACKEND_INSTANCE_ID` 永久不成立，
UI 就卡在「后端离线」。Electron 侧代码注释其实早已自认这条路是错的
（*"the previous broken ps1 restart path"*），但"best-effort"调用被留了下来。
