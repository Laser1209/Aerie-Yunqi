# 实施方案（writing-plans）

需求已经明确、准备动手之前，先产出一份**能照着做**的方案。
方案不是复述需求，而是把"怎么做、怎么验、哪里会出问题"写清楚。

## 铁律

1. **每一步都要有验证方式**。写完"做 X"，紧接着写"怎么知道 X 成了"。
   没有验证方式的步骤等于没定义完成。
2. **按依赖排序，不按心情排序**。先做被依赖的、能尽早暴露风险的。
3. **先跑通最小端到端，再加东西**。绝不为了未完成的复杂度拆掉能跑的部分。
4. **明确写出不做的事**。范围边界比范围本身更容易出事。
5. **不留"以后再换"的临时方案**。要改就直接改到位。

## 步骤

1. **列改动清单**：哪些文件/模块会动，各自改动性质（新增/修改/删除）。
2. **排依赖顺序**：标注哪些步骤必须串行、哪些可以并行。
   指出**关键路径**——最慢的那条链决定了整体进度。
3. **定验证**：每步的可执行验证命令或可观察结果。
   优先用项目里已有的测试/脚本，不要新造一套。
4. **列风险**：2~4 个最可能出问题的地方，每个给出**早期信号**与应对。
5. **收回滚**：如果做了一半发现方向错了，怎么退回去。

## 输出形态

```
## 目标与完成标准
（一句话 + 可判定的成功条件）

## 改动清单
| 文件/模块 | 性质 | 说明 |

## 步骤（按依赖排序）
1. … → 验证：`命令` / 观察到 …
2. …

## 关键路径与并行机会
- 串行：…
- 可并行：…

## 风险
- 风险 → 早期信号 → 应对

## 明确不做
- …

## 回滚方式
- …
```

## 反面例子（不要这样）

- 方案里全是"优化一下""完善逻辑"这类无法判定完成的动词。
- 一步做完所有事，失败时不知道是哪一步坏的。
- 列了 20 步却没有任何一步写验证方式。
