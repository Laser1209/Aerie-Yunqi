## 〇、核心设计理念（贯穿所有模块）

> [!quote] 伪主观性 Principle（v2 收敛版 + v3 决策日志补充）
> 技术层面无法实现真正的"主观意志"，因此系统**只给候选、让伊塔做选择**——把"外部条件触发"包装成"伊塔自己的决定"。
>
> 具体手法（贯穿各系统）：
> 1. **候选生成**：系统按确定性规则+随机因子生成 2–3 个候选（话题/动机/行为/移动目标）。
> 2. **选择包装（确定性）**：候选选择用**加权随机 + 最近做过降权**（Utility AI 模式），不额外调用 LLM。
> 3. **叙事化（LLM）**：LLM（`siliconflow-light`）只在**动机句生成**环节介入，**按需延迟触发**，失败走模板兜底。
> 4. **保底**：LLM 失败/超时 → 确定性兜底，绝不阻断链路。
> 5. **决策日志（v3 新增）**：所有"候选→选择→动机句"**全量落盘**（`decision_log`，append-only），供世界仪表盘实时展示与后台复盘——用户可看到她每时刻从哪几个候选中选了哪个。
>
> **分层原则**：决策层 = 确定性（Utility AI 加权随机），叙事层 = LLM（动机句按需生成），**证据层 = 决策日志**（全量落盘）。

## 一、修缮目标

| # | 系统 | 目标 |
|---|---|---|
| 1 | 话题管控 | 建立话题追踪与生命周期判定；主动消息获得上下文依托，消除"上下文割裂"；话题可存根、可再造 |
| 2 | 行为调度 | 时间档细化、行为资源库（按 zone 聚合绑定行为）、动态每日规划（跨天一次性生成，规则+随机） |
| 3 | 寻路感知 | 位置沿路径行进（非瞬移）；**呈现式智能避障（不穿越桌椅板凳家具）**；对话中能感知"正在移动/目标/周边物件"；轨迹可记录 |
| 4 | 研判 | 排查对话干扰隐患、仿真测试、技术规范文档、与现有架构的取舍记录 |
| 5 | 管理平台（v3 新增） | **候选决策日志**可视化（她每时刻从哪些候选中选了哪个）；**后台管理平台**（聊天记录/分层记忆/状态文件/知识库向量库 增删改查 + 软删回收站 + 热加载）；**数据统计看板**（token/高频话题/常待地点/常做事情/决策统计，图表呈现） |

**核心验收主张**：主动发消息时能接上上一个话题（或明确开启新话题）；问她"你在干什么"能答"正在去厨房/主卧"；她的行动是"她选的"而非"系统推的"；前端蓝点从床边走到门口会绕过餐桌/衣柜不穿模；**世界仪表盘可看到她每时刻的候选与选择；点主 logo 5 次弹出管理平台，可删改聊天记录/记忆（48h 内可恢复）、查看统计图表（懒加载 + 进度条）**。

## 二、现状分析（探索结论）

### 2.1 话题管控缺失 —— 主动消息上下文割裂根因
- **无"当前活跃话题"运行时追踪机制**：全库搜索 `active_topic/current_topic` 无命中。最接近的是 `evolution_manager.detect_topics()`（离线关键词主题识别，仅用于反思摘要/记忆标签）与 `companion_state.PendingTopic`（只驱动主动关怀，无生命周期判定）。
- **根因定位**：[companion.py `_dispatch_push`](file:///e:/Agent_reply/core/companion.py#L3312) 调用 `brain.generate_push(template, mood, tone_hint, judge_context, knowledge_fragment, date)`——**只注入场景模板+情绪+话术原则，完全没有最近对话历史/活跃话题**。因此伊塔发"在干嘛"时不知道上一条在聊什么。（注：`judge_context` 已携带"用户离线时长/情绪强度/desire 分数"，llm_caller.py L826-835。）
- **对话历史**：`Pipeline._load_history()`（pipeline.py L2401）有 `legacy_limit=20` 的读取能力，但只用于对话上下文，未接入主动消息。
- **沉寂检测时钟盘点（v2 修正）**：实际四处时钟、仅两处活——
  - `push_event_engine._last_user_activity`（L179），4h 触发 USER_IDLE_LONG → **活**；
  - `desire_engine._last_user_ts`（L136）→ `user_absence_hours` → 注入 judge_context（llm_caller.py L827-829）→ **活，且是唯一真正喂给 LLM 的静默信号（v1 漏报）**；
  - `evolution_manager.DreamConsolidator.is_idle`（5min，L205）→ **生产未接线**；
  - `proactive_care_governor._silence_elapsed`（2h，L26）→ **参数化传入、模块自身不维护时间戳，生产未接线**。

### 2.2 时序行为粗放
- **5 个 phase**（`world_simulation.py` L36-77）：night/morning/noon/afternoon/evening，每档 2–6 小时，粒度粗。
- **活动静态映射**：phase→location/activity 写死（`_ENVIRONMENT_OBJECTS` L83-89），`_ACTIVITY_TOPIC_PREFIXES`（L96-103）每 activity 固定 2 个视觉话题。
- **无每日规划**：没有"当天计划表"概念，行为完全由时钟决定；随机仅 `_RANDOM_EVENT_POOL`（L119-128）纯文本占位。
- **主动消息 12 场景**（`config/proactive.yaml`）：8 cron + 3 trigger + 1 force 启动，模板固定字符串。
- **第二套 phase 映射（v2 新增发现；v3.2 已升级为单一真源下沉）**：[companion.py `_time_of_day_phase()`](file:///e:/Agent_reply/core/companion.py#L553-L564) 硬编码 5 段区间，与 `DEFAULT_WORLD_PHASES` 平行维护；另有月相集合 `if phase in ("night","evening")`（L3080/L3134）与 phase→中文/光线翻译表（L512-522）、`proactive_candidates.py` L75 的 `topic=f"{phase}:{activity}"`。**档位变更若不同步改这 5 处，会出现快照与生图上下文静默不一致（v3.2 方案：新建 `world_phase.py` 收拢全部 phase 定义，见 §3.2.1）。**

## 三、变更方案

### 系统一：对话上下文与话题管控系统

#### 3.1.1 新增 `core/topic_tracker.py` —— 话题追踪引擎
- **话题模型**：
  ```python
  @dataclass
  class Topic:
      id: str
      subject: str            # 核心主旨/围绕主体（话题的灵魂）
      state: str              # active | paused | closed
      started_at: str
      last_active_at: str
      turn_count: int
      summary: str            # 复用分桶摘要的引用（bucket 索引范围），不自建摘要管线
      stub: str               # 存根：closed 后保留的浓缩记忆
  ```
- **生命周期状态机（v3.2 收敛：paused 派生化）**：Topic 只显式维护 `active | closed` 两态；`paused` 为**派生状态**——`last_active_at` 距今 ≥ 沉寂阈值（如 4h）即视为 paused 语义（供续接判定），**无需显式状态转移路径**（对齐 Temporal"状态由时间/事件派生"模式，省一个状态转移路径）。`closed` 话题保留 `stub`，可被"话题再造"唤醒为 active。状态机只允许单向流转，错判可自愈。
- **话题终止判定标准（v2 修正：砍掉"拆解充分（LLM 判定）"）**——原标准①是任务型 Agent 语义，与陪伴型闲聊不匹配。保留：
  1. **收尾信号**：对话出现明确收尾（"好了""那先这样""明天再说"）或用户转向新主体（确定性收尾词表，可扩展）。
  2. **沉默超时**：paused 超过阈值（如 24h）自动 closed（确定性）。
- **判定策略（v2 修正：砍周期 LLM 判定，保留触发判定）**——原方案"每 5 轮轻量 LLM 判定"是串行 LLM 往返、只服务低频主动消息，且与既有分桶摘要管线（pipeline.py L2315）重复：

#### 3.3.2 移动状态机 —— 新增 `core/movement.py`
- **MovementManager**：
  ```python

      status: str              # idle | moving | arrived
      from_zone: str
      to_zone: str
      path: list[str]          # zone 序列（叙事/日志层）
  ```

## 七、质量验收标准

0. **测试方法论（所有阶段通用，v3.1 用户补充；v3.2 收敛为 rubric 分级 + 自适应维度）**：本文所有测试用例均处于**脱离原文本对话情境及原人设的逻辑推理状态**——用例不得依赖既定对话上下文或角色设定去"猜答案"，而必须用多样化的语句覆盖表达方式与场景的多样性。具体要求：
   1. 每个测试目标覆盖 **≥3 个维度**的同类型语句（按目标自适应选取，不强求固定 6 维度）；
   2. 每个维度包含**代表性测试用例**（含边界情况）；
   3. **LLM 叙事型输出用 rubric 分级**（0-2 分 × 3-5 判据，而非单一 pass/fail——非确定性输出两次结果不同，"全过才放行"不可复现）；**确定性逻辑（A*/phase 映射/状态机）用硬断言**；
   4. 测试过程**详细记录各维度测试结果**（维度 / 用例 / 期望 / 实际 / 通过与否）落盘（如 `work_progress/` 下分阶段测试记录文件）；
   5. **全部维度通过验证后**方可判定该阶段通过并进入下一步流程（rubric 达阈值即通过）。
   - 建议维度（按表达方式与边界划分，具体维度随测试目标调整）：① 直接陈述（"你在干什么"）；② 间接/隐含（"你在哪儿呢"）；③ 口语/随意（"干嘛呢"）；④ 边界情况（极短 / 极长 / 空输入 / 多义 / 重复）；⑤ 情绪或语境偏移（调侃 / 负面 / 急切 / 方言化）。**原"正式/书面表述"维度对确定性逻辑（A*/phase）无意义，仅在 LLM 叙事目标下使用**。每个维度须与测试目标强相关，且至少含 1 个代表性用例。

1. **测试**：每阶段新增单元/集成测试全绿；**全量回归失败数 = 0**（基线按三要素冻结：`git rev-parse HEAD` + 完整 pytest 命令 + 日期，见 §3.4.2；"638 passed/0 failed"为历史文件值不可引用）。
2. **话题**：用户追问"你发的什么/刚才聊的什么"可回答；主动消息无上下文割裂（聊完看书→沉寂→续接看书）；跨天"话题再造"仍可召回。
3. **行为**：DailyPlan 每天不同（随机因子生效）但行为合理；visual_topic 全部命中翻译表（无英文 token 泄漏）。
4. **移动**：连续询问行进状态 5 次，移动中位置单调推进（不跳变；前置：movement 实时派生，不走 60s 快照缓存）；到达后状态为 arrived。
5. **避障**：主卧床→门绕床、客厅→阳台绕沙发两场景，A* 路径与障碍矩形无交（射线-矩形相交断言）；前端蓝点沿 waypoint 折线行进、不穿家具图形。
6. **伪主观性**：触发链路日志可见"候选→加权随机选择→动机句→兜底"；LLM 全挂时链路仍走确定性兜底；动机句仅叙事点触发（默认 0 调用/天）。
7. **决策日志（v3 新增）**：三类埋点（话题动机/行为/移动）各有事件；日志含完整候选集 + chosen + fallback 标记；`/api/cognition/recent` 返回最新 30 条；按日切片轮转不丢数据；世界仪表盘可看到"候选列表 + 选中高亮 + 动机句"。
8. **管理平台（v3 新增）**：入口连点 5 次带计数反馈弹出；**初始不加载（启动时无管理窗口/无预载）**；点击后进度条分阶段推进、首屏 5s 出 KPI、主界面不阻塞；聊天记录/记忆软删后正常历史不可见、回收站可恢复、purge 后物理删除；删除必弹警告（含条目数 + 保留期文案）；级联清理后摘要/记忆/向量三处计数归零（向量 purge 期才删）；状态重置走引擎方法生效。
9. **统计看板（v3 新增）**：token 日趋势与 SQL 直查对拍一致；高频话题基于类目词表；地点/行为卡片 P2 前显示占位；ECharts 本地 vendor 无 CDN；"好看"验收六条可断言指标（token 色值/圆角/栅格/无 emoji 图标/图表类型匹配/5 秒测试）逐条通过。
10. **性能**：移动推进纯内存；话题判定触发式；A* ≤100 点微秒级；统计端点 SQLite 直查毫秒级；管理平台懒加载不拖慢主进程启动。
