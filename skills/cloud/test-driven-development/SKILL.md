# 测试驱动开发（test-driven-development）

先写一条会失败的测试，再写代码让它通过，最后清理。**每一步都要真的跑过。**

## 铁律

1. **没见过红的测试等于没写**。写完测试必须先跑一次，确认它**因为预期原因**失败。
   一条从没失败过的测试，你不知道它在测什么。
2. **只写让当前测试通过的最少代码**。不要顺手把下一个功能也实现。
3. **一次只加一条测试**。批量写十条测试再一起跑，失败时你分不清是哪条的需求没满足。
4. **测试要能因真实缺陷而失败**。如果改坏功能测试还过，那它测的是实现细节，不是行为。
5. **不为了测试而测试**。不要给"测试框架本身""纯粹的 getter"这类无逻辑代码写测试。

## 步骤

1. **写一条测试**，描述**可观察的行为**，不是内部调用序列。
   测试名要说清"什么情况下得到什么"。
2. **跑它，确认失败**（红）。失败信息必须是"功能还没实现"，
   而不是"导入写错""断言写反"——后者说明测试本身有 bug。
3. **写最少实现**（绿）。此时允许写得丑，先把行为跑通。
4. **再跑一次全量**，确认没弄坏别的（回归）。
5. **重构**（重构）。消除重复、改善命名，**每次都保持全绿**。
6. 回到第 1 步，加下一条。

## 该测什么

优先测**边界与失败路径**，它们才是缺陷聚集地：

- 空输入 / 缺字段 / 类型不符
- 刚好在边界上的值（0、1、上限、上限+1）
- 外部依赖失败（超时、返回错误、返回空）
- 重复调用（幂等性）
- 并发/顺序敏感的行为

## 反面例子（不要这样）

- 一次写完 10 个测试，然后花两小时查为什么全红。
- 测试里 mock 掉了要验证的核心逻辑，测完等于没测。
- 为了让测试通过而修改断言（而不是修代码）。
- 断言"函数被调用了一次"这种实现细节——重构时它必碎，且抓不到真实缺陷。
