# 执行计划（executing-plans）

当已经有一份写好的实施方案、需要**一步步落地并逐段验证**时走这份流程。目标是把计划变成可交付的改动，每个检查点都能证明"这一步真的成了"，而不是一口气改完再整体撞墙。

## 铁律

1. **一次只推进一步**：完成当前步骤并通过验证，再开始下一步；不要提前把后面的工作顺手做完。
2. **每步结束必须验证**：跑该步约定的命令或观察预期结果，未通过就不进入下一步。
3. **偏离计划要显式说明**：发现计划有误，先说清"为什么不能照做、改怎么做"，而不是默默改路子。
4. **保持可回退**：每步改动尽量独立，出错能单独撤销，不要把整份计划压成一次大改。
5. **不扩大范围**：计划外顺手发现的"顺便优化"一律不做，记下来留到计划完成后单独评估。
6. **进度要留痕**：每完成一步，把该步的改动与验证结果记一行，作为进度与回滚依据。

## 步骤

1. **确认起点**：读计划，锁定当前这一步，明确它的验收标准与依赖是否已满足。
2. **执行该步的改动**：按计划指定的文件/模块动手，只做这一步要求的事。
3. **跑验证**：执行该步的验证命令或观察预期结果，记录实际输出。
4. **判定**：通过则标记该步完成并进入下一步；不通过则定位原因，先修到通过。
5. **更新进度**：写下步骤编号、改动摘要、验证结果，必要时更新后续步骤。
6. **遇到计划缺陷则暂停**：给出"原计划哪条不成立、替代做法、影响哪些后续步骤"，确认后再继续。
7. **全部完成后整体回归**：跑一次全量测试或检查，确认各步之间没有互相破坏。

## 输出形态

```
## 进度
- [x] 步骤1 建表 → 验证：`pytest tests/test_schema.py` 通过
- [ ] 步骤2 …

## 本次改动
- 文件 / 性质（新增|修改|删除）/ 说明

## 验证结果
- 命令：…  输出：…

## 偏离与原因（若有）
- 原计划：…  实际：…  影响：…
```

## 反面例子（不要这样）

- 没跑验证就宣称"这一步完成了"。
- 一步里顺手改了三个不相关模块，出问题无法归因。
- 计划明显行不通还硬着头皮走完，最后整体推倒重来。
- 把整份计划压成一次大提交，中途出错只能全部回滚。
