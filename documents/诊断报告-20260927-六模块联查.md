## 1. 微信连接（P0，已修复）

### 证据链

- `logs/main.log` 17:16–17:21 三次重复崩溃栈：
  `ILinkProtocolError('ret must be an integer')`
  → `communication/ilink/models.py:60 _integer`
  → `models.py:220 GetUpdatesResponse.from_dict`
  → `communication/ilink/client.py:85 get_updates`
  → `core/ilink_gateway.py:117 _poll`，`Task ... done ... exception=...`
- 真机探测（已存凭据实调 `POST /ilink/bot/getupdates`，HTTP 200）：成功包体只有
  `{"msgs": [], "sync_buf": "...", "get_updates_buf": "..."}`——**成功时根本没有 ret 字段**。
- `core/ilink_gateway.py` `_poll()` 只兜了 RateLimit / SessionExpired / 5xx HTTP / 网络错误，
  未兜 `ILinkProtocolError`，一个空消息轮询就把整个通道任务打死，状态永离 connected。

### 修复（已做）

1. `communication/ilink/models.py:220`：`ret` 改可选，缺失即 0。
2. `core/ilink_gateway.py`：`_poll` 捕获 `ILinkProtocolError`，退避重试（游标仅在解析成功后推进，重试安全）。
3. 78 个 ilink 测试全过。

### 修复前后对比（运行时证据）

- 修复前：首个 poll 即 `ret must be an integer`，任务死亡，前端无法连接。
- 修复后：后端连续多轮 `getupdates 200`（00:25:30 起约每 18s 一次），零协议异常，
  `GET /api/ilink/status` → `phase=connected, configured=true, connected=true`。

### 1b. 微信连上后不回消息（P0，已修复）

前一版报告把根因记为「配对码闭环完全缺失」。当前事实源已变化：`POST /api/ilink/pairing-code`
已存在并有测试覆盖，真正的现场故障是**下面四条叠加**（2026-09-27 复查）：

1. **整批解析失败 → 游标永不推进**。`GetUpdatesResponse.from_dict` 遇到任何一条格式异常的
   消息就整体抛 `ILinkProtocolError`，游标不推进，于是**每一轮都重复解析同一批并再次失败**——
   表现就是「connected 但永远收不到消息」。现改为逐条容错，丢弃坏消息、保留可用消息，
   并把 `skipped_messages` 计数出来。
2. **`client_id` / `create_time_ms` 被当必填**。iLink 部分消息确实不带这两个字段，
   旧代码直接抛错 → 又走回第 1 条的死循环。现均为可选（缺失 → 空串 / 0）。
3. **出站 `send_text` 用 `data.get("ret") != 0` 判成功**。iLink 成功响应经常**不带 `ret`**，
   `None != 0` 为真 → 抛错 → 配对之后依然发不出微信。现改为「缺失即视为 0，仅显式非零才失败」。
4. **库里根本没有绑定设备**（本次实测 `data/ilink_state.db` → `ilink_bindings` **0 行**，
   而 `ilink_sessions` 有 1 行、`ilink_pairing` 有 1 条待用配对码）。即：会话凭证在、
   长轮询在跑、状态显示 connected，但**没有任何被授权的用户**，所有入站消息按设计被丢弃。
   这就是「内部连接成功却完全不回复」的最终解释。

修复内容：

- `communication/ilink/models.py`：逐条容错 + `skipped_messages` + 两字段可选。
- `communication/ilink/client.py`：`ret` 缺失即成功。
- `communication/ilink/channel.py`：入站全程可观测（收到/丢弃/原因），
  并对**未绑定设备**在收到第一条消息时回一条配对引导
  （「我还没认下这台设备。把云栖面板上那串 8 位配对码发给我，就能开始聊了。」，
  10 分钟最多提示一次），把「绝对静默」变成「有反馈」。
- `core/ilink_gateway.py`：`_poll` 增加总 `except Exception` 兜底并退避，避免单点异常打死长轮询。

> **仍需用户操作**：在微信里向机器人发送 8 位配对码完成绑定（码从云栖面板取）。
> 绑定前机器人只会回上面那句引导语，这是设计行为，不是故障。

## 2. 图像生成

### 2a. 9/26 午夜「图片这次没发出来」=世界闸门关闭（与 #3 同根）

- `logs/main.log` 23:52–23:58 四条：
  `[ChatPhoto] delivered status=disabled reason=world_disabled consumed=False`
  与截图时间（23:57/23:58）完全吻合。
- 链路：`core/pipeline.py:1281 _deliver_chat_photo` →
  `Companion.publish_image_candidate`（`core/companion.py:1633`）→
  world outbox 发布/消费；`world_port` 为 `NullWorldAdapter` 时
  `control/publish` 一律 `world_disabled`（`core/world_port.py:237/243`）。
- 即这次图根本没走到生图 provider，前置闸门就拒了。修好世界模块（#3）即解除。

### 2b. 「再拍一张」行为错误（P1）

- `electron/src/renderer/js/chat.js:428-436`：点击后把 `retry_text` 填入输入框并调 `this.send()`
  ——把用户原指令当**一条新消息**重发（还会再走一遍意图识别/分条），不是重跑生图。
- 同一气泡 `_upsertImageStatusBubble`（chat.js:441-476）直接 `appendChild`，
  **绕过 chat-store 排序**，是 #4 气泡错位的来源之一。
- 正确做法：调 `POST /api/images/generate`（`core/api_server.py:2450`），
  用原 prompt_key/user_raw/size/reference_assets/persona_id 组参，新幂等键（`:retry<n>`），
  不产生用户消息；图片状态气泡改走 store upsert。

### 2c. provider 层历史失败（P0，已核实并修复）

- 9/25 19:38 有 `image provider network call failed` / `image edit provider call failed`；
  `core/llm_caller.py` 的 `generate_image` 是 stub，真实链路在
  `LLMCaller.generate_image`（绑定到 `_brain_generate_image`）→ OpenAI 兼容
  `POST {IMAGE_GEN_BASE_URL}/images/generations`。
- **本次实测（逐源探活）**：
  - `image2.inian.one`（旧配置）：TCP 可连、`/v1/models` 401，但 generations / edits
    **POST 全部挂起 ReadTimeout**（不是拒绝，是不响应）——旧配置下生图必然卡死。
  - `api.codexgood.com`（`OPENAI_*`）：**403 "User has been banned"**。
  - `api.siliconflow.com`：`/models` 200，但生图端点 **SSL 握手持续超时**。
- 叠加本地「假成功」语义：`publish_image_candidate` 曾把「已发布候选」直接当
  `completed` 上报，工具层据此记成功 → 用户看到"发了"但实际没有图。已改为
  **只有 consumer 回报 `status == "completed"` 才算成功**，否则 `failed`。
- **修复（零代码改动，仅切配置）**：改用智谱 BigModel CogView-4 ——
  `IMAGE_GEN_BASE_URL=https://open.bigmodel.cn/api/paas/v4/`、`IMAGE_GEN_MODEL=cogview-4`、
  `IMAGE_GEN_API_KEY=<BIGMODEL_API_KEY>`。响应形态与 OpenAI 完全一致
  （`{"created","data":[{"url"}],"id","request_id"}`），原样兼容既有 payload
  （`n`/`size`/`response_format=b64_json`）。
- 另给 `_brain_generate_image_edit` 补了错误分类：404/405 → `image_edit_unsupported`，
  超时/网络 → `provider_network_error`，让「图生图不可用」快速失败并回落文生图，
  不再挂死。
- 遗留：现用源没有 edits 端点（人物参考图锁定降级）。已在局部特写提示词里补
  **文字外貌锚点**，使自拍一致性不再单点依赖图生图（详见 §7.3）。

## 3. 世界模块第二波启动（P0）

### 3.1 sidecar 数据库无限膨胀（直接卡死启动）

- `data/world_sidecar/world.db` = **1,065 MB（1.1GB）**：
  `world_outbox` 845,303 行、`world_state_snapshot` 845,197 行。
- `world_service` 全目录 grep 无任何 `DELETE/prune/retention/VACUUM`；
  `world_service/main.py:40` 默认 `tick_interval_seconds=1.0`，
  `storage/sqlite_store.py:47,65` 每 tick 各插一行 → 一天 8.64 万行、约 100MB/天。
- `plugin-supervisor.js:408-451` start 要在 `startupTimeoutMs` 内完成
  ready 行 + `/hello` 握手 + `/state` 读取；GB 级库恢复/查询直接超时
  → `startup_failed`/`recordCrash`，表现为「第二波起不来」。
- 修复：
  1. 立即处置：停 sidecar 后对两表做保留窗口清理（如 outbox 仅留 ACK 后 N 条/7 天，
     snapshot 每 N tick 留 1 条 + 保留最近 M 条）并 `VACUUM`；
  2. 长期：sqlite_store 增加 tick 内增量修剪（保留上限+年龄），加用户态
     `POST /api/world/maintenance` 或启动前自动修剪；
  3. tick 快照降频（状态未变不写 / 改 5–10s 一档）。

### 3.2 双世界架构与状态不一致

- 存在两个世界：后端进程内 `InProcessWorldAdapter` 与 Electron 监督的 sidecar
  （`world_service.main`）。`build_world_port`（`core/world_port.py:659-707`）
  先试 sidecar（env endpoint/token 缺失即记 `failed to initialize remote world adapter`，
  日志 17:13/17:14 多条），再回退 inprocess。
- `data/runtime_config.json` rev14：`world_sidecar_v1=false`、
  `world_process_supervision_v1=false`、`world_runtime_loop_v1=false`、
  `world_desired=running`——即运行时层关了 sidecar，但静态 `config/settings.yaml`
  三 flag 均为 true；仪表盘「功能 enabled=true」来自静态值，
  Electron 实际不 spawn（`main.js:2265-2305` 三条件与运算）。
- 当前实测后端：`/api/world/dashboard/snapshot` = `running/simulated`（进程内世界正常 tick）。
  午夜 disabled 疑似当时后端 world_port 曾被
  `POST /api/world/runtime/bind` connection=null 覆盖为 NullWorldAdapter
  （该路径已有 InProcess 保护，`api_server.py:896-905`，需确认当晚运行版本是否含此修复）。
- 修复方向：统一「单一世界模式」事实源——运行时 flag 决定时，静态面板不得显示 enabled；
  inprocess 模式下隐藏/禁用 sidecar 生命周期控件，避免两套状态互相覆盖。

## 4. 消息排序、时间戳、气泡错位（P1）

- 存在双渲染路径：`chat-store.js:77-160` 有 `insertSorted`/`sortKey{ t,b }`/upsert 重排，
  正常消息（用户、助手分片、typing）走 store；但
  `chat.js:441` 图片状态气泡、审批卡片等直接 `appendChild` 到消息容器，完全不受排序约束
  → 异步任务中这些气泡先于/后于用户消息出现，截图所示倒置由此产生。
- 时间戳同源：`core/chat_request_repository.py:225-233 submit_batch` 对一批用同一个
  `_timestamp()`；截图同一轮三条助手消息同为 `00:08:04`。前端同秒依赖
  insertCounter/domId tiebreak，但旁路 append 的元素没有序号。
- 用户消息异步回填：乐观气泡、typing 占位与真实消息 upsert 在长任务期间可能晚于助手节点，
  重排只覆盖 store 内节点。
- 修复：所有气泡（含 image-status/approval/tool 状态）一律走 store upsert；
  后端每个分段独立时间戳（段内可保留批次 id），store tiebreak 用
  `(ts, batch_seq, insertCounter)`；回填用户消息时强制重排整列。

## 5. 「生成中」状态体验（P2）

- 现状：`chat.js:1776` request 状态文案 `running: "生成中"`，
  样式 `main.css:1645` 的 badge；与「排队中」一样挂在气泡旁，语义不清（实际是 AI 处理中）。
- 方案：running 时在助手头像前显示三点跳动 typing 气泡（复用现有 typing 样式），
  不出文字 badge；排队中保留可取消 badge。注意宿主只能是助手节点（chat.js:1791 注释已有此约束）。

## 6. 连续多句被拆成独立任务（P2）

- `core/message_batcher.py:133-173` 现语义：首条**零等待立即 dispatch**（Gate4 为修 D5 刻意改的），
  运行中到达的才进 pending。空闲时连打两句 → 第一句立刻开跑，第二句成为下一批 → 上下文断裂。
- 方案（需权衡首条延迟）：首条派发前加可配置短静默聚合窗（建议 1.2–2.0s，
  沿用 `window_seconds`，timer 内续到消息则重置，上限 max_batch_size）；
  本地桌面/QQ 同通道一致生效；设置页可开关与调窗长。

## 7. 本轮（2026-09-27 二次联查）修复与证据

本节记录本轮实际改动、验证方式与结论。症状之间的关联先在 §7.1 说清，再逐项列证据。

### 7.1 三个症状的关联（为什么它们看起来"互相独立"其实同源）

```
        ┌──────────────── 共享「沉默失败」语义 ────────────────┐
        │                                                      │
   [微信不回复]              [QQ 回复内容错]           [生图完全失效]
        │                          │                          │
   入站/出站协议容错缺失      输出端清洗缺失           外部依赖失效 + 假成功
   + 无绑定设备               (通道标记回显)           (provider 挂/封 + published 当 completed)
        │                          │                          │
        └──────────┬───────────────┴──────────────┬───────────┘
                   │                              │
        共同放大因素：错误被吞、状态上报与实际不符、无降级路径
```

- **共同点**：三处都是「本地认为成功、外部实际失败」——微信是 `connected` 但无绑定、
  QQ 是把内部元信息当正文发出去、生图是把 `published` 当 `completed`。
  所以排查顺序应是**先做端到端可观测性（探针），再修协议，再修语义**。
- **耦合点**（改动时的风险面）：
  - `core/companion.py` 同时被主动消息链路与生图链路依赖 → 改它必须两套回归都跑。
  - `communication/ilink/*` 被长轮询、配对、状态 API、pipeline 四处依赖 → 改 `models.py`
    必须跑 ilink 全量（status/pairing/pipeline）。
  - `core/llm_caller.py` 既管文本 provider 又管生图 provider → 改错误分类要跑
    `test_llm_caller_provider_routing.py`。

### 7.2 症状①：微信「连上不回」— 详见 §1b

改动文件：`communication/ilink/models.py`、`communication/ilink/client.py`、
`communication/ilink/channel.py`、`core/ilink_gateway.py`。

实测事实源：`data/ilink_state.db` → `ilink_sessions` 1 行 / `ilink_pairing` 1 行 /
**`ilink_bindings` 0 行** → 确认「已连接但无授权设备」是现场状态。

### 7.3 症状③：生图完全失效 — 详见 §2c

- **决定性验证（纯配置、无任何 env 覆盖）**：
  `CFG_OK=1`，`base=https://open.bigmodel.cn/api/paas/v4/`、`model=cogview-4`，
  走完整 `ImageWorkflow.generate_image` → `status=completed`，
  产物落盘 242,577 字节 PNG。
- 另有两条独立验证：真实 `LLMCaller.generate_image` 返回 `status=ok`、
  `b64_len=89500`（解码 67,123 字节 PNG）；完整工作流一次落盘 572,209 字节，

## 9. 出站元信息泄漏（`[00:05] [桌面]`）——同一个 bug 的第三次复发

用户截图：QQ/微信端收到 ``[00:05] [桌面] 怎么一直没动静...肯定是累坏了``。
桌面端显示正常，只有外部通道露标记。

### 9.1 根因（实测定论，非推测）

把截图原文喂给既有清洗链，**两条正则的匹配结果都是空**：

| 检查项 | 结果 |
|--------|------|
| `_TIMESTAMP_MARKER_RE.findall("[00:05] [桌面] x")` | `[]` — 正则要求**带日期**（`\d{2,4}-\d{2}`），模型把日期砍掉了 |
| `_CHANNEL_MARKER_RE.findall("[00:05] [桌面] x")` | `[]` — 正则锚定 `^` 行首，`[桌面]` 被 `[00:05]` 顶到行中间 |
| 对照 `[09-27 00:05] [桌面] x` | 能清洗 → **所以之前"看起来修好了"** |

两条正则互为前提：通道标记那条**依赖时间戳先被剥掉**才能落到行首。
时间戳形态一变（少了日期），整条链同时失效。

更深层原因（这才是要害）：
- 清洗函数在**三个地方各存一份**：`communication/qq_client.py`、
  `core/pipeline.py`、`core/model_output.py`；
- **`ILinkGateway.send_text` 一份都没有**——微信端裸发。

所以「桌面端正常、QQ/微信端露标记」不是偶然，是**只在一部分通道上做了防护**的必然结果。

### 9.2 修复：收敛为唯一实现，所有通道出口都过它

新增 `core/model_output.sanitize_outbound_text` 作为**出站唯一闸门**，
顺序固定：剥标签 → 剥元信息标记 → 剥伪图片语法。标记识别改为
**行首连续标记串整体剥除**（`[00:05] [桌面] ` 一起走），不再依赖剥除顺序；
并覆盖 `[话题：…]` 前缀。

| 位置 | 改动 |
|------|------|
| `core/model_output.py` | 成为唯一实现：收编 `strip_thought_action_tags` / `strip_fake_image_markdown`，新增 `strip_internal_markers` / `sanitize_outbound_text` |
| `communication/qq_client.py` | 删掉本地 4 个清洗函数与 3 条正则，改调 `sanitize_outbound_text`（3 处：send_message / 分段 / 图片说明） |
| `core/ilink_gateway.py` | **新增出口闸**（此前完全没有）；空内容直接不发送并告警 |
| `communication/send_queue.py` | 节拍计算改用同一实现，避免"标记被算进打字时长" |
| `core/content_validator.py` | 有效性判定改用同一实现，保证「校验说能发」＝「真的能发」 |
| `core/pipeline.py` | 删除重复的 `_HIST_LABEL_RE` 与 `_strip_leading_timestamp`（生产从未调用，仅测试引用） |

### 9.3 超级验证（拦截真实上线字节）

不只测函数返回值，而是**拦截传输层**看用户实际收到什么：
