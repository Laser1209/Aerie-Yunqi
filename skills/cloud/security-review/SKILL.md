# 安全审查（security-review）

当用户要求对代码 diff / MR / 提交做安全审查时使用。
**只报本次变更引入、且能说清怎么被利用的风险**，不报背景噪音——报告的价值在于可行动，不在于条数。

## 铁律

1. **只报本次变更引入的**：老代码里本来就有的问题不占篇幅，除非本次改动让它变得可利用。
2. **必须给出可利用路径**：写清 入口（谁能触发）→ 数据流（输入怎么到危险点）→ 后果。说不出路径的降级为"存疑"。
3. **按危害排序**：高危（可导致 RCE / 数据泄露 / 越权）在前，低危在后；没有高危就明确写"未发现"。
4. **每条给修复方式**：具体到改哪个函数、换成什么 API，不给"注意校验"这种空话。
5. **区分"可证实"与"存疑"**：无法确认的标 `待确认`，写清还需要什么信息才能判定，不要当结论下。
6. **不臆造上下文**：看不到调用方就明说"以下判断基于当前 diff，缺调用方信息"。

## 步骤

1. **圈定范围**：确认审查对象（diff / 文件 / PR）与目标分支基线，只看改动及其直接影响面。
2. **找入口点**：列出改动暴露给外部的入口——HTTP 路由、消息消费、文件与参数解析、反序列化、模板渲染、命令拼接、DB 查询。
3. **追数据流**：从入口一路追到危险操作，检查中间是否经过校验、转义或参数化。
4. **过重点类别**：路径穿越、SSRF、注入（SQL / 命令 / 模板）、不安全反序列化、XSS、越权与鉴权缺失、硬编码凭据、日志泄露敏感信息、新引入依赖的已知漏洞。
5. **确认可利用性**：对每条候选追问"攻击者能否控制输入、有无前置条件、影响是什么"，答不全就降级为存疑。
6. **写报告**：按危害排序，逐条给 位置（文件:行）→ 类型 → 利用路径 → 修复。
7. **给结论行**：末尾一句总评——能否合并、有哪些必须先修。

## 输出形态

```
## 结论
- 建议：可合并 / 修复后再合并（阻塞项 N 条）

## 发现
### [高危] <一句话标题>
- 位置：path/to/file.py:123
- 类型：命令注入
- 利用路径：谁能触发 → 数据如何到达 → 后果
- 修复：改为 subprocess.run([...], shell=False) 并做白名单校验

## 待确认
- 缺 X 上下文，无法判定 …

## 未发现
- 已检查：路径穿越 / 反序列化 / 越权 …
```

## 反面例子（不要这样）

- 列了 15 条"建议"，却没有一条能说清怎么被利用。
- 把 `eval` 出现在老代码里当成本次引入的问题报上来。
- 结论只写"存在安全风险，建议加固"。
- 把"可能""也许"当成高危上报，制造噪音。
